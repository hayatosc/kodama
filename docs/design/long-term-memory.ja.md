# 長く動き続けるエージェントの長期記憶

状態：提案。
この文書の内容はまだ実装していない。
英語版は [long-term-memory.md](long-term-memory.md) にある。

Kodama のエージェントは、常駐するボットのように使うことを想定している。
1つのエージェントが同じ会話で何週間も何か月も、返事と作業を続ける。
この文書は、エージェントが大事なことを覚えたまま、それ以外を手放す仕組みを提案する。
目的は、モデルに渡す文脈も、Durable Object（以下 DO）の保存領域も、際限なく増えないようにすることである。
あわせて、すべてのデータを DO に置く形は採らない。
DO に置くのは Pi Durable のセッション（文脈と会話の記録）だけにし、長期記憶は別の置き場に移す。

## 何が問題か

いまの kodama では、1つのエージェントが SQLite を使う DO 1つに対応し、その DO が Pi Durable のセッションを持っている。

### 文脈はすでに縮められる

Pi Durable には、古い会話を要約して文脈を縮める **compaction** が組み込まれている。
kodama は compaction の設定をしていないので、既定値（`reserveTokens` 16384、`keepRecentTokens` 20000、`backgroundTokens` 32768）で自動に動いている。
モデルが見る量については、すでに上限がある。

### 保存領域は減らない

Pi Durable のエントリ（会話の1件ごとの記録）は不変で、消されない。
仕様書には「head は以後の文脈を変えるだけで、古いエントリをストレージから消さない」とある（Pi Durable spec §2.1）。
compaction も `reset()` も、モデルに見せる範囲の先頭を動かすだけである。
終わったタスクの記録や、システムプロンプトのセクションが変わったときの記録も残り続ける。
Pi には、これらを削る API が無い。

### DO の上限は 10 GB

SQLite を使う DO は、1つあたり 10 GB（無料プランは 1 GB）が上限である。
上限に達すると、書き込みは `SQLITE_FULL` で失敗する。
読み取りと削除はできるが、エージェントとしては動けなくなる。

### 要約にすべては残らない

Pi の要約は、コーディングエージェントと同じ構造化したチェックポイントの形式で作られ、前回の要約を引き継ぐ（spec §8.7）。
既定としてはこれで十分である。
それでも、どんな要約も回数を重ねると細部を落とす。

- **要約ドリフト**：圧縮のたびに、まれな細部が黙って捨てられる（arXiv 2603.07670）。
- **上書きと検索の差**：原文を残して検索で戻せる方式は、どの圧縮頻度でも再現率が 0.95 前後だった。要約で上書きする方式は 0.33〜0.56 で、圧縮の頻度が高いほど悪かった（arXiv 2607.08032、小規模な実験）。

対策は、Pi の要約を自前のものに置き換えることではない。
事実と生の記録を要約の外に持っておくことである。

### 終わらない1セッションは学習にも悪い

Hermes Agent のドキュメントは、Discord などのチャットについてこう書いている。
リセットしないと1つのセッションが何週間も続き、伸び続ける履歴に compaction が繰り返し走って高くつく。
さらに、忘れる、記憶から思い出す、過去のセッションを検索する、という学習のループがほとんど回らない。
Grok Bot のように同じ会話を担当し続ける使い方は、まさにこの状況にあたる。

## Cloudflare の費用はどこで出るか

価格は Cloudflare の料金ページ（Workers Paid、2026年10月時点）から取った。
無料枠はアカウント全体で1か月あたりの量である。

| 項目                        | 価格                                                          | 無料枠     |
| --------------------------- | ------------------------------------------------------------- | ---------- |
| DO の稼働時間               | 100万 GB 秒あたり 12.50 ドル。動いている間、128 MB 分で数える | 40万 GB 秒 |
| DO または D1 の行の書き込み | 100万行あたり 1.00 ドル（削除も数える）                       | 5,000万行  |
| DO または D1 の行の読み取り | 100万行あたり 0.001 ドル                                      | 250億行    |
| DO の SQLite の保存量       | 1 GB 月あたり 0.20 ドル                                       | 5 GB       |
| D1 の保存量                 | 1 GB 月あたり 0.75 ドル                                       | 5 GB       |
| R2 Standard の保存量        | 1 GB 月あたり 0.015 ドル                                      | なし       |
| R2 の書き込みと読み取り     | 100万回あたり 4.50 ドルと 0.36 ドル                           | なし       |

1つのエージェントが1日8時間モデルの出力をストリームし、それを30日続けた場合を見積もる。
無料枠を使い切ったあとの追加分として数えている。

| 費用の出どころ                                                                                                      | 見積もり                   | 減らし方                          |
| ------------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------------------------- |
| ストリーム中の Pi の進捗の書き込み。100 ms（`progress.partialIntervalMs`）ごとに最大1回コミットし、1回で1行以上書く | 860万行以上、8.6 ドル以上  | 間隔を広げる                      |
| モデルの応答を待つあいだの稼働時間                                                                                  | 10万8,000 GB 秒、1.35 ドル | モデルが動く間は避けられない      |
| `subscribe()` のストリームを1日中開けておく（ハイバネーションしない）                                               | 32万4,000 GB 秒、4.05 ドル | 誰も見ていないストリームを閉じる  |
| 会話の記録 1 GB を DO に置いておく                                                                                  | 月 0.20 ドル               | R2 にアーカイブする（0.015 ドル） |

進捗のコミット1回で何行書くかはまだ測っていない。
段階1で、結合テストの中で `SqlStorageCursor.rowsWritten` を使って測る。

ここから2つのことが言える。

1. **大きな費用は書き込みの量と稼働時間であり、保存しているバイト数ではない。**
   データを DO の外に出しても、この2つは減らない。
   減らせるのは、Pi の進捗の間隔とストリームを開けておく時間である。
2. **長期記憶は、エージェントの DO に置くべきではない。**
   1行あたりや 1 GB あたりで比べると、DO は D1 より高くない。
   それでも長期記憶を DO の外に置く理由は3つある。
   - 長期記憶はセッションより長く残る必要があるが、セッションの DO は保存領域を空けるために丸ごと消す。
   - 長期記憶はエージェントの間で共有したい。
   - UI や整理の処理が、エージェントの DO を起こさずに長期記憶を読めるようにしたい。

## 設計を決める9つの知見

調査で分かったことのうち、設計に直接効くものを並べる。

1. **原文は取り出せる形で残す。**
   検索で戻せる圧縮は、要約で上書きするだけの圧縮より強い（2607.08032）。
   OpenClaw も Hermes も Cloudflare も生の履歴を残している。
   よく使う保存領域から消すのはかまわないが、唯一の写しを消してはいけない。
2. **compaction は Pi に任せる。**
   Pi はすでに、切れ目を選び、構造化した形式で要約し、前回の要約を引き継ぎ、失敗したらやり直し、文脈があふれたときにも立て直す。
   自前の要約が効くという根拠は、別の場面のもの（ACE が書き直すのは会話ではなく手引き）か、ベンダー自身の測定（Factory）である。
   要約を自前で持つと、そのプロンプト、失敗、劣化まで kodama が背負うことになるが、得られるものははっきりしない。
   観測マスク（古いツール出力を伏せる。2508.21433）も同じ種類の最適化なので、ツール出力が文脈の大半を占めると測れてから考える。
3. **記憶は compaction からではなく、会話の記録から抽出する。**
   OpenClaw が compaction の直前に記憶を書き出すのは、文脈がエージェントの見る唯一の場所だからである。
   kodama では compaction は保存領域から何も消さないので、エントリは世代交代まで `scanEntries` で読める。
   抽出は、エージェントがアイドルになったあとに裏で行えばよく（Grok Build や Hermes と同じ）、世代交代の前には必ず行う。
4. **抽出したものは確かめる。**
   記憶システムの誤りは抽出と更新の段階で生まれて溜まる（HaluMem、2511.03506）。
   抽出した内容は原文と突き合わせて確かめ、出どころを付けて保存する。
5. **事実と出来事では寿命が違う。**
   事実は時間で薄れさせず、新しい事実で置き換える。
   出来事は新しさで順位を下げる（2604.11364、Zep の辺の無効化、Generative Agents の減衰係数 0.995）。
   モデルは古くなった事実をそのまま受け入れがちなので（STALE、2605.06527 で正答率 55.2%）、置き換えは明示的に記録する。
6. **スキルは、検証できた経験から作る。**
   成功して検証できた軌跡から作ったスキルは効いた（AWM で相対 24.6% と 51.1%、ASI で 23.5%、ReasoningBank）。
   作業の前にエージェント自身が書いたスキルは、スキル無しより 8.1〜11.5 ポイント悪かった（SkillsBench）。
   小さく絞ったスキルのほうが大きな束より良く、更新を重ねると散らかる（SkillEvolBench）。
   一覧から選ぶ精度は、64個を超えたあたりから落ちる（2607.10113）。
   使われないスキルは片付ける必要がある（Hermes の curator は14日で stale、30日でアーカイブし、自動では消さない）。
7. **共有の記憶は、攻撃と不整合の入口になる。**
   ふつうの利用者でもエージェントの記憶に細工できる（MINJA）。
   悪意ある「成功体験」を植え付けると、長く残る（MemoryGraft）。
   既存のプロンプトインジェクション対策では、記憶の汚染を防げない（MPBench）。
   共有ブロックを複数のエージェントが同時に丸ごと書き直すと、更新が失われる（Letta）。
   共有の書き込みには、出どころ、記録ごとに1人の書き手、レビューが要る。
8. **常に読み込む記憶は、区切りでだけ変える。**
   Hermes は、プロンプトのキャッシュを効かせるために記憶をセッション開始時に固定している。
   Pi も、セクションが変わるとそれを新しいシステムエントリとして送り直す。
   常に読み込む記憶は、アイドルのときか世代交代（後述）のときだけ更新する。
9. **記憶には専用の書き手を置く。**
   Letta は、記憶の編集を会話するエージェントから外し、別の sleep-time エージェントに移した。
   記憶の管理と会話を1つのエージェントにまとめると、遅くなり、信頼性も落ちたからである。
   会話するエージェントに残したのは検索のツールだけである。
   Cloudflare Agent Memory も「主のエージェントは、保存の戦略に文脈を使うべきではない」と書いている。
   Hermes は記憶の見直しを安いモデルで走らせることができる（3〜5倍ほど安くなる）。
   書き手が1人なら、知見7の不整合の問題も片づく。

## 設計

### 保存の層

| 層         | 置き場                                | 中身                                                                                   | 寿命                                 |
| ---------- | ------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------ |
| セッション | エージェントの DO（いまのまま）       | いまの世代の Pi Durable セッション、常に読み込む記憶の写し、最近のリクエストの受付記録 | 1世代。終わったら丸ごと消す          |
| 長期記憶   | D1 のデータベース `MEMORY_DB` 1つ     | 記憶の記録と FTS5 の索引、共有の記憶への提案、スキルの索引と変更記録、世代の索引       | 残す                                 |
| アーカイブ | R2 のバケット `ARCHIVE`               | 過去の世代の会話の記録（JSONL と SHA-256 付きの目録）、スキルの本体                    | 保持期間の規則で決める               |
| 記憶係     | Cloudflare Workflows `MemoryWorkflow` | 仕事ごとに1回の実行。ステップの結果は保存される                                        | 1回の実行                            |
| 任意       | Vectorize                             | 記憶の記録の埋め込み                                                                   | 検索の取りこぼしが見えたときだけ足す |

DO のクラスは増やさない。
エージェントは Worker のバインディングを通して D1 と R2 を読む。
長期記憶を書くのは記憶係だけである。

長期記憶を D1 に置くのは、次の理由による。

- FTS5 による全文検索が使える。
- 30日分のどの時点にも巻き戻せる（Time Travel）。
- UI の Worker や整理の処理が、エージェントの DO を起こさずに読める。

D1 のデータベースは1つ 10 GB までだが、記憶の記録は小さい。
もし足りなくなっても、D1 は小さなデータベースを多数に分けて使う前提で作られているので、エージェントのまとまりごとなどに分けられる。

### 記憶の範囲

| 範囲                                                   | 中身                                                                         | 誰が書くか                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------- |
| **文脈**                                               | いまのターン、compaction の要約                                              | セッションの DO の中の Pi          |
| **エージェント**（`agent:<id>`）                       | そのエージェントのメモ、身につけた約束ごと、出来事、そのエージェントのスキル | 記憶係                             |
| **共有**（`shared:<space>`、たとえば `shared:global`） | チームの約束ごと、共有の事実、共有のスキル                                   | 記憶係（レビューを通ったものだけ） |

人ごとの記憶は持たない。
一緒に働く人についての事実が仕事に関わるなら、それはふつうのエージェントの事実として残す。

### 記録の形

```text
memory_records(
  id            -- 内容から作るハッシュ: hash(scope, kind, key?, content)
  scope         -- agent:<id> | shared:<space>
  kind          -- fact | event | instruction | task
  key           -- 事実と指示の話題キー（正規化したもの）
  content
  provenance    -- JSON: agentId, generation, エントリの範囲, tool, writer
  observed_at, created_at
  superseded_by -- この記録を置き換えた記録の id
  invalid_at    -- 矛盾が見つかった時刻
  importance, use_count, last_used_at, pinned
)
memory_fts      -- content と key に対する FTS5
```

種類ごとの寿命は次のとおり。

- **fact（事実）**：薄れさせない。同じ話題キーの新しい事実が来たら置き換え、置き換えの鎖を残す。
- **event（出来事）**：新しさで順位を下げる（半減期は設定でき、既定は OpenClaw と同じ30日）。保持期間を過ぎたらアーカイブする。
- **instruction（指示）**：複数の手順からなるものは、統合処理でスキルの候補にする。
- **task（タスク）**：終わったら、または世代交代のときに捨てる。そのとき残っているタスクは引き継ぎメモに書く。

本当に消す（プライバシーのための削除）のは運用者の操作であり、エージェントにはさせない。

### 常に読み込む記憶

Pi のプロンプトセクションとして、上限付きのブロックを出す。
中身は、エージェントのメモと、小さな共有ブロックである。
各ブロックには文字数の予算があり、使用量をプロンプトに表示する（Hermes は `[67% — 1,474/2,200 chars]` のように出している）。
セッションの DO は、世代の始まりと、アイドルのあいだに記憶係から実行の完了を知らされたときに D1 からブロックを読み、表示する内容を Pi のドキュメントに写しておく。
そのあいだのリクエストはこの写しを使うので、プロンプトの先頭が変わらず、リクエストごとに D1 を待つこともない。

### 記憶係

長期記憶の書き手は1人にする。
これを**記憶係**と呼ぶ。
仕事をするエージェントは、記憶を読むことと、覚えてほしいことを頼むことだけをする。

- **何か**：Cloudflare Workflow（`MemoryWorkflow`）であり、kodama のエージェントではない。仕事ごとに新しく実行し、仕事をするエージェントとは別のモデルの設定（ふつうはより安いモデル）を使う。自分の会話を持たないので、compaction も世代交代も要らない。
- **なぜ Workflow か**：ステップの結果が保存され、失敗したステップはやり直されるので、途中で止まった仕事も終わったステップを繰り返さずに再開できる。さらに、Workflow はモデルの応答を待つあいだ CPU 時間として課金されない。同じ待ち時間でも、DO の中なら稼働時間として課金される。
- **1つのエージェントに同時に1つの実行**：実行の ID をエージェント ID とチェックポイントから作り、D1 のチェックポイントは比較してから進める（compare-and-set）。2つの実行が同じ範囲を書くことはない。
- **仕事をするエージェントのツールは少なくする**：`memory_search`、`history_search`、`skill_search`、`skill_load`、`remember` だけを持つ。`remember` は D1 の受付箱に頼みごとを書き、記憶係の実行をすぐに始めさせる。記憶の記録そのものは書かない。

### 書き込みの経路

ここに挙げる書き込みは、どれも記憶係が行う。

**1. 覚えてほしいという頼み。**
仕事をするエージェントの `remember` の呼び出しは、valibot で検証し、大きさに上限を設け、インジェクションの型を検査したうえで受付箱に入る。
記憶係は次の実行でそれを記録にする。
ほかの書き込みと同じく、既存の記録との照らし合わせを通す。

**2. 抽出。**
エージェントがしばらくアイドルになったとき（セッションの DO のアラーム）と、世代交代の前に必ず、セッションの DO が記憶係の実行を始める。
Pi の compaction には手を出さない。

1. そのエージェントの抽出の区切り（チェックポイント）より後のエントリを、セッションの DO のページ単位の RPC で読む（中では `scanEntries` を使う）。
2. 安いモデル（設定で選ぶ）で、記録の候補を抽出する。
3. 各候補を、根拠として挙げたエントリと突き合わせ、裏付けの無いものは捨てる。
4. D1 の既存の記録と照らし、追加する、置き換える、無効にする、何もしない、のどれかを選ぶ（Mem0 の ADD、UPDATE、DELETE、NOOP に近いが、削除せず置き換える）。
5. 書き込みと同じバッチで、D1 のチェックポイントを進める。

記録の id を内容から作り、`INSERT OR IGNORE` で書くので、途中で止まってやり直しても重複して書かない。

**3. 統合。**
多くて1日1回程度、D1 に対する定期の実行として走らせる。
エージェントの DO の中では走らせない（sleep-time compute や、OpenClaw と Devin の dreaming と同じ発想）。
重複をまとめ、矛盾を解消し、出来事の順位を下げ、常に読み込むブロックを予算内に作り直し、スキルを作り、共有の記憶への提案を用意する。
作り直しは差分の編集で行い、丸ごと書き直さない。
根拠が要るときは、R2 にアーカイブした会話の記録を読む。
抽出は決まった手順の流れでよいが、統合では記憶係にツールを使わせる。
根拠を探しに行き、何をまとめるかを判断する必要があるからである。

### 読み出しの経路

- 常に読み込むブロック（前述）。
- `memory_search`：D1 の FTS5 の BM25 に、新しさと重要度を掛けて並べる。結果には出どころも付ける。
- `history_search`：D1 の世代の索引（引き継ぎメモと要約）を探し、当たった世代の会話の記録を R2 から読む。抽出で取りこぼした細部を拾う安全網になる。

### compaction

compaction は Pi の仕事である。
kodama は Pi の既定値をそのまま使い、計測の結果が必要を示したときだけ `src/harness.ts` で方針を変える。
あとでツール出力が文脈の大半を占めると分かったら、要約に手を入れる前に、`beforeRequest` フックでの観測マスクを試す。

### セッションの保存領域を空ける世代交代

Pi はエントリを消せない。
そこで、セッションの DO を丸ごと消し、引き継ぎメモから始め直す。
この方式を**世代交代**と呼ぶ。
長期記憶は D1 にあるので、同じ DO と同じエージェント ID のまま世代を替えられる。
世代ごとに別の DO を作って振り分ける仕組みは要らない。

世代交代は、セッションがアイドルのときだけ、次のどれかを満たしたら行う。

- `ctx.storage.sql.databaseSize` が閾値を超えた（たとえば 1 GB）。
- その世代での compaction の回数が上限を超えた。長く続いた要約の鎖ではなく、整理した記憶から次の世代を始めるためである。
- 長いアイドルのような、区切りのよい時点が来た（Hermes も区切りで `/new` することを勧めている）。

手順の進み具合は D1 の世代の索引に記録し、再起動しても途中から続けられるようにする。

1. エージェントの設定を保存し、世代 N を「書き出し中」にする。
2. 最後のエントリまでを対象に記憶係の実行を始め、終わるまで待つ。
3. 世代 N を R2 へ分割して書き出し、目録を書き、件数とハッシュを確かめる。
4. 引き継ぎメモ（Pi の最新の compaction の要約と、残っているタスク）を世代の索引に保存する。
5. `blockConcurrencyWhile` の中で、harness を閉じ、`ctx.storage.deleteAll()` を呼び、Pi を開き直し、設定を戻し、引き継ぎメモから始め（`reset(handoff)`）、最近のリクエストの受付記録を書き、アラームを張り直す（この互換日付では `deleteAll()` がアラームも消すため）。そして世代 N+1 を有効にする。

手順5の前にメッセージが届いたら、世代交代はやめて後でやり直す。
kodama は最近のリクエスト ID の受付記録を小さな表に持つので、切り替えのあとでも再送や `submission()` が正しく答えられる。
購読していたストリームは閉じるので、クライアントは接続し直す。
クライアントはもともと、置き換えのスナップショットを受け入れる作りになっている。
`deleteAll()` が消した行の数だけ課金されるかは、まだ確かめていない。
どちらにしても、DO が大きくなる前に世代を替えれば、その量は抑えられる。

### スキル（手続きの記憶）

- **形式**：Agent Skills（`name` と `description` を前書きに持つ `SKILL.md`）。Hermes、OpenClaw、Claude Code と互換にする。
- **置き場所**：索引（名前、説明、範囲、状態、使用回数、R2 のキー）は D1 に、本体と付属のファイルは R2 に置く。
- **見せ方**：プロンプトのセクションには、名前と説明を多くても数十個だけ並べる。残りは `skill_search` で探し、`skill_load` で R2 から本体を読む。
- **作り方**：記憶係が統合の中で、少なくとも2回成功した手順だけを候補にする。候補には根拠の軌跡と、失敗から学んだ注意点を付ける。再実行かチェックに通ったら有効にし、共有のスキルはさらにレビューを通す。仕事をするエージェントはスキルを書かず、作業の前にスキルを書くこともしない。
- **片付け**：14日使われなければ stale、30日でアーカイブする。固定（pin）したものは対象外にする。アーカイブは元に戻せ、すべての変更を書き手と一緒に記録する。

### 共有の記憶と安全

- 共有の記録は直接書かない。複数のエージェントが頼っているエージェント範囲の記録から、記憶係が出どころ付きの提案を作り、レビュー役が受け入れるか退ける。レビューの UI ができるまでは、運用者の RPC で行う。
- 共有の記録は、記録ごとに書き手を1人に決める。更新はブロックを書き直さず、新しい版を作る。
- 信頼できない出どころから来た内容は、出どころ付きの証拠として残すだけにし、レビューなしで常に読み込む記憶には上げない（OpenClaw も信頼できない報告を同じように扱う）。
- 秘密情報は保存しない。書く前に伏せる（Codex と Grok Build も秘密情報を記憶から外している）。

### 費用を抑える手段

- 1回のコミットで何行書くかを測ったうえで、`progress.partialIntervalMs` を広げる（たとえば 500〜1000 ms）。代わりに、UI に流れるストリームの更新が粗くなる。
- 誰も見ていない `subscribe()` のストリームは閉じる。あるいは、観測を WebSocket のハイバネーションに移す。
- セッションの DO が大きくなる前に世代を替える。アーカイブした分は、R2 に置くと保存の単価がおよそ13分の1になる。
- 記憶係は Workflow で動かす。モデルを待つあいだ CPU 時間は課金されないが、同じ待ち時間でも DO の中では稼働時間として課金される。
- 統合は、エージェントを1つずつ起こさず、D1 に対する1つの定期ジョブで行う。

## 進め方

どの段階でも、モデルをモックした workerd の結合テストを一緒に入れる。

1. **計測と費用の削減。**
   進捗の間隔を明示し、1ターンあたりの書き込み行数、DB の大きさ、文脈の大きさを測る。
   テスト：1ターンあたりの行数が記録した予算を超えないこと。
2. **D1 の長期記憶と記憶係。**
   スキーマとマイグレーション、`MemoryWorkflow` による抽出とチェックポイント、受付箱と `remember`、読み出しのツール、常に読み込むセクションを入れる。
   テスト：何度か compaction を経る前に話した事実が、あとで D1 に見つかること。新しい事実が古い事実を置き換えること。途中で止まった抽出をやり直しても重複して書かないこと。抽出が失敗してもチェックポイントは進まず、会話には影響しないこと。
3. **同じ DO での世代交代。**
   R2 への書き出し、世代の索引、`history_search`、受付記録を入れる。
   テスト：どの手順の途中で DO が追い出されても世代交代が完了すること。切り替えをまたいでリクエスト ID の重複排除が効くこと。書き出しの確認が済むまで保存領域を消さないこと。
4. **スキル。**
   D1 の索引、R2 の本体、見せ方、統合処理からの提案、片付け。
5. **共有の記憶。**
   共有の範囲、記憶係からの提案、レビュー。
6. **評価。**
   compaction と世代交代のあとに、確認の質問をする（事実の想起、触ったもの、続きから再開できるか、決定の理由。Factory の評価と同じ観点）。
   LongMemEval と同じ観点で、知識の更新、時間に関する質問、答えないべきときに答えないか、も確かめる。

## 検討して採らなかった案

- **すべてを DO に置く**（エージェントごとと共有の範囲ごとに記憶用の DO を作る）。
  動きはするが、セッションを消すと記憶も消えるので外へ写す必要がある。
  共有の記憶には起きたままの DO が別に要り、UI や整理の処理が読むたびにその DO を起こすことになる。
- **1つのセッションの DO を使い続ける。**
  いちばん簡単で、テキストの会話だけなら 10 GB はかなり遠い。
  しかし保存領域を空ける手段が無く、要約のドリフトも続き、上限に当たると止まる。
  段階1と2はこの形のままでも動くので、世代交代は計測の結果を見てから入れてもよい。
- **記憶を R2 の markdown ファイルだけで持つ**（OpenClaw や Hermes がディスクに置くのと同じ形）。
  保存はいちばん安く、人が手で直しやすい。
  しかし検索には別の索引が要り、R2 にはトランザクションが無い。
  D1 の記憶を人が読むための markdown として書き出す機能は、あとから足せる。
- **仕事をするエージェントが自分で記憶を書く**（この計画の前の版）。
  すべてのリクエストに記憶のツールと指示が載り、仕事用のモデルを記録の管理に使い、1つの範囲に書き手が何人もいることになる。
  Letta も同じ理由でこの形をやめている。
- **記憶係を kodama のエージェントにする**（自分の Pi セッションを持つ DO）。
  自分の会話の記録が溜まり、それ自体の世代交代が要り、モデルを待つあいだ稼働時間が課金される。
  記憶係の仕事には、長く続く会話が要らない。
- **compaction の要約を自前で持つ**（Pi の `beforeCompact` フックで記憶を抽出し、足し込み式の要約を返す）。
  記憶が Pi の compaction の処理に縛られ、Pi の要約が問題だという根拠も無いまま、要約の質を kodama が背負うことになる。
  評価の確認質問で、記憶と `history_search` では補えない取りこぼしが見えたときのために、フックは選択肢として残しておく。
- **Pi Durable に削除の機能を頼む。**
  有効な先頭より前のエントリを消すのは、Pi の「エントリは不変」という前提や fork の仕組みとぶつかる。
  上流に提案する価値はあるが、それを待つほどではない。
- **Cloudflare Agent Memory を使う。**
  この設計とよく似ていて、`cf` にはすでに `agentMemory` のバインディングがある。
  ただし非公開ベータなので、記憶の保存先はインタフェースの裏に隠しておき、あとで差し替えられるようにする。

## 決めてほしいこと

- 共有の記憶の提案をレビューするのは誰か（UI を通した人か、規則を厳しくした記憶係か）。
- アーカイブした会話の記録をどれだけの期間残す必要があり、誰が消してよいか。
- 記憶係にどのモデルを使い、どれだけの費用をかけるか。
- 書き込みを減らす代わりに、UI に流れるストリームの更新をどこまで粗くしてよいか。
