# 長期記憶

状態：提案。

英語版は [long-term-memory.md](long-term-memory.md) にある。

Kodama のエージェントは、1つの会話で何週間も何か月も動き続ける。
この設計では、大事なことをエージェントの DO の外にある長期記憶に残し、Pi のセッションは DO に置いたままにし、セッションの古い行を消して保存領域が増え続けないようにする。

## 部品

| 置き場              | バインディング | 中身                                                                                          |
| ------------------- | -------------- | --------------------------------------------------------------------------------------------- |
| エージェントの DO   | `AGENTS`       | Pi Durable のセッション。常に読み込む記憶とスキル一覧の写し。古い行の削除の状態。alarm の予定 |
| `MemoryAgent` の DO | `MEMORY_AGENT` | 記憶係（インスタンスは `memory` の1つ）と、その仕事の列                                       |
| D1 のデータベース   | `MEMORY_DB`    | 記憶の記録、適用した操作、revision、アーカイブの目録、スキル、提案、変更記録                  |
| R2 のバケット       | `ARCHIVE`      | アーカイブしたエントリとその検索の索引（`archive/`）、スキル（`skills/`）                     |

```text
AgentService（公開の RPC の入口）
  `-- AGENTS ---------------------> Agent DO（agentId）  ここから MemoryAgent には届かない

Agent DO（agentId）
  |-- 読む -----------------------> D1 MEMORY_DB         memory_search、アーカイブの目録、revision
  |-- 書く -----------------------> D1 MEMORY_DB         使用回数、アーカイブの目録（削除のとき）
  |-- read（SkillsEnv）-----------> R2 ARCHIVE           SKILL.md と付属のファイル
  |-- 読み書きする ---------------> R2 ARCHIVE           アーカイブしたエントリと索引、history_search
  `-- MEMORY_AGENT.enqueue -------> MemoryAgent DO       remember、extract、record_archive

MemoryAgent DO（"memory"）
  |-- 読み書きする ---------------> D1 MEMORY_DB
  |-- 読み書きする ---------------> R2 ARCHIVE           アーカイブしたエントリ、スキルの blob
  |-- AGENTS readEntries ---------> Agent DO             抽出のためにエントリをページ単位で読む
  |-- AGENTS memoryJobSettled ----> Agent DO             仕事の結果。知らせであって記録ではない
  `-- AGENTS memoryChanged -------> Agent DO             読み直しの知らせ。記録は revision

scheduled ハンドラ -------------> MemoryAgent DO       consolidate（1日1回）
```

記憶の記録とスキルを変えるのは記憶係だけである。
仕事をするエージェントが書くのは、使用回数と、古い行を消すときの自分のエントリのアーカイブの目録だけである。

## 記憶の形

### 範囲

| 範囲                                         | 中身                                             | 書くもの                           |
| -------------------------------------------- | ------------------------------------------------ | ---------------------------------- |
| `agent:<agentId>`                            | そのエージェントのメモ、約束ごと、出来事、スキル | 記憶係                             |
| `shared:<space>`（たとえば `shared:global`） | チームの約束ごと、共有の事実、共有のスキル       | 記憶係（チェックを通った提案だけ） |

人ごとの範囲は持たない。
エージェントが読む共有の範囲は `sharedSpaces` に並べる。
`sharedSpaces` は `AgentConfig` に足す項目で、既定は `["global"]` であり、`tools` と同じように検証する。

エージェントの記録は、`overrides` に共有の記録の ID を入れられる。
そのエージェントでは、エージェントの記録が共有の記録の代わりになる。
ただし共有の記録が `required = 1`（チームの決まり）なら、エージェントの記録は読み込まず、統合がそれを `invalid` にして変更記録に残す。
ほかのエージェントは共有の記録をそのまま使う。

### 種類

| 種類          | 寿命                                                                 |
| ------------- | -------------------------------------------------------------------- |
| `fact`        | 薄れさせない。ID を指して置き換える新しい記録でだけ置き換わる        |
| `instruction` | `fact` と同じ。複数の手順からなるものはスキルの候補にする            |
| `event`       | 新しさで順位を下げる（半減期30日）。保持期間を過ぎたらアーカイブする |
| `task`        | 終わったら捨てる                                                     |

`origin` は `user_request`、`agent_judgment`、`extraction`、`consolidation`、`proposal` のどれかである。
アーカイブしたエントリの要約は記憶の記録にせず、R2 でアーカイブしたエントリの隣に置く。
本当に消すのは運用者の操作とする。

### D1 のスキーマ

スキーマは Drizzle で [schema.ts](../../packages/agents/src/memory/schema.ts) に定義する。
`pnpm db:generate` が D1 のマイグレーションを `packages/agents/migrations` に書き、`cf d1 migrations` で適用する。
Drizzle では書けない FTS5 のテーブルとトリガーは、手で書いたマイグレーション `0001_memory_fts.sql` にする。

| テーブル                 | 1行が表すもの                                                       |
| ------------------------ | ------------------------------------------------------------------- |
| `memory_records`         | 記憶の記録1件                                                       |
| `memory_fts`             | `memory_records.search_text` に対する FTS5 の索引（トリガーで同期） |
| `memory_ops`             | 適用した書き込みの操作1件と、その結果                               |
| `scope_revisions`        | 範囲ごとの、常に読み込む記録とスキルの revision                     |
| `extraction_checkpoints` | エージェントごとの、抽出を終えた最後のエントリ                      |
| `archive_segments`       | R2 にアーカイブした範囲1つの目録                                    |
| `skills`                 | スキルの索引。名前、説明、状態、内容のハッシュ                      |
| `skill_writes`           | ファイルを上書きする前に記録したスキルの更新                        |
| `skill_usage`            | エージェントごとのスキルの使用回数                                  |
| `shared_proposals`       | 共有の記憶への提案と、その判断と適用                                |
| `memory_ledger`          | すべての変更を追記だけで残す記録。断った候補も残す                  |

### 書き込みの適用

記憶係が行う変更は、どれも `op_id` を持つ操作である。
ツール呼び出しの `op_id` は、仕事の ID と Pi のツール呼び出しの ID から作る SHA-256 である。
記録済みのツール呼び出しを実行しなおしても、同じ `op_id` になる。
コードで行う仕事では、仕事の ID と手順から作る。

1. `memory_ops` を `op_id` で引く。行があれば、その `result_json` を返し、何も変えない。
2. 対象を読み、操作の前提を確かめる。たとえば、置き換える記録が `active` で、操作が指定した revision であること。前提が崩れていれば何も書かずに `conflict` を返し、候補は変更記録に残して後でもう一度判断する。
3. 1つの `batch()` を送る。中身は、条件付きの更新（`WHERE id = ? AND status = 'active' AND revision = ?`）、新しい記録の普通の `INSERT`、変更記録の行、`scope_revisions` の加算、`memory_ops` の行である。

書き込みに `INSERT OR IGNORE` は使わない。
記録の ID の重複か、すでに使った `op_id` があれば文が失敗し、`batch()` が操作全体を取り消す。
`memory_ops` の行は条件付きの更新の直後に `guard = changes()` で入れ、`guard` は 1 でなければならないので、どの行にも当たらなかった更新もバッチ全体を取り消す。
記憶係は仕事を1件ずつ処理する（[仕事](#仕事)を参照）ので、手順2で読んだ内容は手順3まで変わらない。
制約は、その前提が崩れたときの最後の守りである。
仕事をするエージェントが更新するのは `use_count` と `last_used_at` だけで、これらは `revision` を変えない。

ほかの規則は次のとおり。

- 置き換えは古い記録を ID で指す（`memory_supersede(oldId, oldRevision, content)`）。書く前に、記憶係が `memory_search` で候補を探す。話題キーは持たない。新しい記録は古い記録と同じ範囲に置く。ほかの範囲の記録を変えるときは、`overrides` か共有の提案を通す。
- 記録の id：範囲、種類、内容、元のエージェント、元の最初のエントリから作る SHA-256。
- `superseded_by` は外部キーにしない。D1 は外部キーをその場で検査するが、古い行を更新するのは新しい行ができる前だからである。
- エントリの ID は使い回されないので、チェックポイントとアーカイブの範囲は、エージェントとエントリの ID だけで識別する。

### 新しさ

仕事を処理する順番は、情報の新しさの順番ではない。
同じ元のエージェントの記録を置き換えたり無効にしたりできるのは、候補の `source_entry_to` がその記録より大きいときだけである。
そうでなければ `memory_supersede` は `stale` を返し、候補は変更記録に断ったものとして残る。
そのため、古い範囲を抽出しても、より新しい `remember` を取り消さない。

エージェントが違えば、エントリの ID は比べられない。
候補が、ほかのエージェントの記録や共有の記録を直接置き換えることはない。
候補は `base_revision` 付きの共有の提案になり、記憶係が決められない食い違いは `conflict` として変更記録に残る。記憶係は今の revision に対して提案し直せる。

### 検索用の文字列

`search_text` には、正規化した単語を空白で区切って入れ、FTS5 は `unicode61 remove_diacritics 2` で索引にする。
記録、アーカイブの索引、問い合わせのすべてで、同じ1つの関数を使って作る。

1. NFKC で正規化し、小文字にする。
2. `new Intl.Segmenter('ja', { granularity: 'word' })` で分け、`isWordLike` の断片だけを残す。
3. 各断片の中で、カタカナの後の `ー` を取り除く（`/([ァ-ヴ])ー+/g` を `$1` に置き換える）。
4. 続いたカタカナの断片を1語にまとめる。
5. 保存する文字列の場合だけ、まとめた語と異なる元の断片を後ろに足す。

問い合わせは、まとめた語をそれぞれ引用符で囲み、空白でつなぐ（FTS5 の `AND`）。
何も返らなければ、元の断片でやり直し、それでも返らなければ、まとめた語をそれぞれ前方一致（`"語"*`）にしてやり直す。
`search_version` にはこの関数の版を入れ、統合が古い版の行を作り直す。

### 問い合わせ

- 常に読み込む記憶：エージェントの範囲と、その共有の範囲にある有効な `instruction` と `fact` を、上の優先の規則で1つに絞り、`pinned`、`importance`、`last_used_at` の順に並べ、コードで文字数の予算に収まるところまでを切り出す。
- `memory_search`：`memory_fts MATCH ?` を、許された範囲の有効な記録とつなぎ、`bm25()` で並べてから、新しさと重要度で並べ直す。返した行の `use_count` を増やし、`last_used_at` を1つの文で更新する。
- `history_search`：[アーカイブの索引](#アーカイブの索引)を参照。

## 記憶係

- `class MemoryAgent extends Agent`。独立した DO のクラスとして公開し、インスタンスは `memory` の1つだけにする。`Agent` を基本的にそのまま継承し、`subscribe`、`snapshot`、`submission` も残す。あとで UI が、認証付きの `AgentService` のメソッドを通して記憶係の処理を見られるようにするためである。
- 今のところ `AgentService` には含めない。仕事は、仕事をするエージェント、古い行の削除、記憶係自身の受理された提案、`scheduled` ハンドラからしか届かない。
- `sendMessage`、`send`、`sendTo` は例外を投げる。仕事は `enqueue` からしか入れず、列を通らない入力は「仕事を1件ずつ」を崩すからである。`cancel` は処理中の仕事を止め、処理する係はそれを失敗と同じくやり直す。
- 設定はコードで固定する。モデルは `MEMORY_MODEL_PROVIDER` と `MEMORY_MODEL_ID` で選び、システムプロンプトは記憶係用のものを使う。`setConfig` は例外を投げる。
- `Agent` に、harness の設定と既定の設定を作る protected なメソッドを足し、`MemoryAgent` はそれを上書きして自分の登録表と固定の設定を渡す。
- 自分の登録表に、`memory_search`、`memory_write`、`memory_supersede`、`memory_decline`、`read_entries`、`skill_write`、`skill_archive`、`shared_propose`、`notify_memory_changed` のツールを持つ。書き込むツールは、どれも変更を操作として適用する（[書き込みの適用](#書き込みの適用)を参照）。`skill_write` が受け付けるのはエージェントの範囲だけである。仕事をするエージェントの登録表には、これらは無い。
- 記憶係自身の Pi のセッションも、ほかのエージェントと同じく古い行を消して空ける。抽出とアーカイブは行わない。

### 仕事

`enqueue(job)` は仕事を valibot で検証し、`memory_jobs` に入れる。
`memory_jobs` は記憶係自身の SQLite にあるテーブルで、Pi のテーブルとは別である。

| 列                            | 意味                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------- |
| `job_id`                      | 主キー。元のエージェント、元のエントリ、内容から作るハッシュ。または提案の ID |
| `kind`、`priority`、`payload` | 仕事の中身                                                                    |
| `status`                      | `queued`、`running`、`settled` のどれか                                       |
| `outcome`                     | 片づいたあとの `persisted`、`declined`、`conflict`、`failed` のどれか         |
| `attempts`、`not_before`      | やり直しの状態                                                                |
| `submission_id`               | モデルを使う仕事の、Pi の受付                                                 |

同じ `enqueue` を繰り返しても、すでにある行を見つけて返す。
`jobStatus(jobId)` で行を読める。

種類は、モデルを使う `remember`、`extract`、`record_archive`（アーカイブした範囲の要約）、`consolidate` と、コードで行う `apply_proposal` である。

処理する係は1つで、`RecoveryAlarm` と同じように順に動き、進行中の仕事を常に1件以下に保つ。

1. `not_before` を過ぎた `queued` の仕事のうち、優先度がいちばん高く、その中でいちばん古いものを取り、`running` にする。
2. モデルを使う仕事なら、会話はアイドルで受付の列も空である。`reset()` を呼ぶと、Pi はアイドルのあいだにその場で置く。続けて、仕事の ID を `requestId` にして、仕事を入力として `submit()` する。どの仕事も新しい文脈で始まる。`submission_id` を記録する。コードで行う仕事は、Pi を使わずにコードで処理する。
3. 受付が片づいたら、その仕事の `memory_ops` と変更記録から結果を決め、仕事を `settled` にし、元のエージェントの `memoryJobSettled(jobId, outcome)` を呼ぶ。
4. そのあとで初めて、次の仕事を取る。

起動したときとアラームのとき、処理する係は `running` の仕事を続ける。
受付が記録されていればその完了を待ち、無ければ同じ `requestId` でもう一度送る（Pi はすでにある受付を返す）。

- 優先度は、`remember` がいちばん高く、次に `apply_proposal` と `record_archive`、次に `extract`、最後に `consolidate` とする。
- 統合は、範囲1つと記録200件までの小さな仕事に分ける。`remember` が待つのは、そのような小さな仕事1件までになる。
- 失敗した仕事は、1分後、10分後、1時間後にやり直し、それでも失敗したら `failed` で片づけて変更記録に残す。

## 仕事をするエージェント

ツールは `memory_search`、`history_search`、`remember` と、スキルを読むための Pi Durable の `read` ツールである。

`remember` は、次のときにそのターンの中で呼ぶ。

- ユーザーが覚えるよう頼んだとき、または続けて守る指示（「いつも」「これからは」）を出したとき。
- エージェントが残すべきと判断したとき。決めたことと理由、ユーザーからの訂正、失敗から学んだこと、調べてようやく分かった長く変わらない事実がこれにあたる。

`remember` は、仕事が列に入った時点で、仕事の ID と一緒に `accepted` を返す。
記憶係のモデルが終わるのは待たない。
仕事はあとで `persisted`、`declined`、`failed` のどれかで片づき、`memoryJobSettled` で知らされ、`jobStatus` でも読める。

残さないものはシステムプロンプトで示す。
作業の途中の状態、まだ固まっていない結論、秘密情報、一度きりの依頼、リポジトリやドキュメントにすでに書いてあることである。
1ターンで受け付ける `remember` は3件までとする。

## 書き込みの経路

### remember

1. 入力を valibot で検証し、大きさに上限を設け、インジェクションの型を弾く。
2. 内容、出どころ（`user_request` か `agent_judgment`）、元のエントリの ID を載せて、`remember` の仕事を列に入れる。`accepted` を返す。
3. 記憶係は内容を分類し、既存の記録と照らして書く。
   - `user_request`：頼まれたとおりに書く。同じキーの前の記録を置き換える。
   - `agent_judgment`：重複や価値の低いものは断ることがある（変更記録に残す）。重要度は低めから始め、使われないままなら統合でアーカイブする。
4. 仕事が片づき、仕事をするエージェントに `memoryJobSettled` が届く。

### extract

仕事をするエージェントがしばらくアイドルになったとき（`extract` のアラーム）と、古い行の削除がチェックポイントの遅れを見つけたときに、列に入れる。

1. `read_entries` で、チェックポイントより後のエントリをページ単位で読む。エージェントの DO から読む（`scanEntries` を使う）か、すでに消した範囲なら R2 の範囲から読む。
2. 記録の候補を抽出する。
3. 根拠として挙げたエントリで裏付けられない候補を捨てる。
4. 既存の記録と照らして、追加する、置き換える、無効にする、何もしない、のどれかを選ぶ。[新しさ](#新しさ)の規則に従う。
5. 各ページの最後の操作で、チェックポイントを進め（`revision` を条件にする）、そのページで終わった範囲の `extracted` を 1 にする。

### consolidate

`scheduled` ハンドラが1日1回、小さな仕事に分けて送る。
重複をまとめ、矛盾を解消し、出来事の順位を下げ、常に読み込む記憶が予算に収まるよう重要度と固定を調整し、古い `search_version` の行を作り直し、スキルを提案し、共有の記憶への提案を作り、適用されずに残った `accepted` の提案を適用する。
さらに、アーカイブした出来事、古い変更記録、残している変更記録からも途中のスキルの更新からも参照されず1日以上たったスキルの blob を、少しずつ消す。
データベースの大きさ（`meta.size_after`）と範囲ごとの記録の数を変更記録に残す。

cron のトリガー（UTC の `17 3 * * *`）が `MemoryAgent.consolidate()` を呼ぶ。
コードでは、30日より古い済んだ仕事と90日より古い変更記録を消し、古い `search_version` の行を作り直し、この1日に変わった範囲ごとに `consolidate` の仕事を1つ列に入れ（200範囲まで）、大きさを記録する。
仕事では、`list_records` で範囲の有効な記録を読み（200件まで。種類ごとに、よく使われた順）、`memory_supersede` と `memory_invalidate` で直す。

## 常に読み込む記憶

Pi のプロンプトセクションが、常に読み込む記憶の問い合わせから2つのブロック（エージェントの記憶と、小さな共有ブロック）を、予算の使用量付き（`[67% — 1,474/2,200 chars]`）で出す。
エージェントの DO は、出す内容と、それを作ったときの `scope_revisions` を Pi のドキュメントに写しておく。
リクエストはこの写しを読む。

写しは、アイドルのあいだに次のときに更新する。

- 起動したとき。
- `memoryChanged` が届いたとき。
- 入力を受け付ける前に、前回 revision を確かめてから60秒を過ぎていたとき。1つの問い合わせでエージェントの範囲と共有の範囲の `scope_revisions` を読み、どれかが新しければ先に写しを作り直す。

知らせが失われても、更新が遅れるのは60秒より後の次のターンまでである。
変更のたびに全エージェントを起こす必要もない。

## compaction

Pi に組み込まれた compaction を既定のまま使う。
kodama はフックを付けず、置き換えもしない。

## alarm

DO が持てる alarm は1つである。
`AlarmSchedule` は、用途ごとの予定時刻を DO の保存領域に持ち（エージェントでは `recovery`、`extract`、`prune`、記憶係では `jobs`）、alarm をいちばん早い時刻に合わせる。
`alarm()` は時刻の来た用途をすべて処理し、alarm を張り直す。
`RecoveryAlarm` は `recovery` の用途になり、走れるタスクが無くなっても、消すのは自分の時刻だけである。

## 古い行の削除

エージェントの DO が、Pi のセッションの古い行をアーカイブしてから消す。

消してよい行は次のとおり。
`P` は、ルートの会話でいちばん新しい境目（head marker）の `head` である。

- ルートの会話の `entries` のうち `id < P` のもの。
- `status = 'terminal'` の `tasks` と、それに属する `documents` と `document_revisions`。
- 以上に対応する `record_ids` の行。

`submissions` は消さない。
Pi は受付に時刻を持たせておらず、`submissionByRequest` はこの行を使って、やり直された要求に最初の結果を返すからである。
入力1つにつき1行で、エントリに比べれば小さい。

エージェントがアイドルになったとき、終わっていない実行があるか、`ctx.storage.sql.databaseSize` が閾値（既定は 1 GB）を超えていて `P` より前のエントリが残っていれば、`prune` のアラームを張る。
この確認は保存領域だけを読むので、harness を開いている途中でも行える。
運用者は `kodama:prune-limits` のキーで、1つの DO の閾値を下げられる。
1回の実行で扱うエントリは 16 MB までとし、ファイルを作る処理が DO のメモリと CPU の制限に収まるようにする。大きさが閾値を下回るまで実行を繰り返す。
状態はエージェントの SQLite にある `prune_runs` テーブルに置き、Pi のテーブルとは分ける。
終わっていない実行は常に1つまでである。

| 状態       | 確かめられていること                                             |
| ---------- | ---------------------------------------------------------------- |
| `prepared` | 前回消したところの次から、`P - 1` までのうちの範囲が決まっている |
| `exported` | エントリ、マニフェスト、索引が R2 にあり、確かめてある           |
| `indexed`  | `archive_segments` の行が D1 にある                              |
| `deleted`  | DO から行が消えている                                            |

起動したときと `prune` のアラームのときに、終わっていない実行をその状態から続ける。

1. **準備。** 範囲を決め、`prepared` にする。抽出のチェックポイントが `P - 1` より手前なら、`extract` の仕事を列に入れる。削除はその完了を待たない。抽出はあとで R2 の範囲から読めるからである。
2. **書き出し。** `archive/<agentId>/<first>-<last>` の下に、エントリ（`.jsonl`）、マニフェスト（`.manifest.json`。範囲、件数、時刻、SHA-256、Pi Durable の版）、コードで作った検索の索引（`.index.json`。[アーカイブの索引](#アーカイブの索引)を参照）を書く。読み戻して確かめ、`exported` にする。キーは範囲だけで決まるので、書き出しを繰り返しても同じオブジェクトを上書きするだけである。
3. **目録。** `archive_segments` の行を入れ、読み戻し、`indexed` にする。そのあとで要約のための `record_archive` を列に入れる。
4. **削除。** `blockConcurrencyWhile` の中でもう一度確かめる。ここで行うのはローカルの SQLite の処理だけなので、30秒の制限には遠く届かない。
   - `harness.inspect()` が、背景の compaction も含めて、生きているタスクを1つも報告しないこと。背景の compaction は、再開するときに記録した `tail` からエントリを読み直すからである。
   - ルートの会話が唯一の会話であること。
   - 列に入った入力の受付も書き込みの受付も無いこと。
   - いちばん新しい境目の `head` が、まだ `P` 以降であること。

   どれかが崩れていれば、実行を `indexed` のままにし、10分後に `prune` のアラームを張る。
   崩れていなければ、harness を閉じ、消してよい行を消し、`deleted` にするところまでを1つの `transactionSync` で行う。
   そのあと harness を開き直し、アラームを張り直す。
   消すエントリはその実行の範囲のものである。最後に `deleted` になった実行の最後のエントリが、消した境目になる。
   そのあいだに届いた要求は、開き直した harness を待つ。

手順1〜3は、エージェントが仕事を続けているあいだに進める。
アイドルが要るのは手順4だけである。

上限の閾値（8 GB）を超えたら、実行が `deleted` に届くまで、`sendMessage` は新しい入力を、やり直せるエラー `storage_maintenance` で断る。
忙しいエージェントも手元の仕事を終えれば、削除がアイドルの機会を得られる。
削除に要るのは R2 と D1 だけなので、記憶係が止まっていても、遅れるのは抽出と要約であり、保存領域の回収は止まらない。

`readEntries` は、消した境目より前の範囲を、アーカイブした範囲から読む。
抽出が遅れていても、すべてのエントリを読める。

記憶係も、自分のセッションを同じ方法で消す。ただしアーカイブはしない。
記憶係のエントリは終わった仕事の作業の跡であり、記録はすでに D1 にあるからである。
仕事の途中で harness を閉じると仕事が失敗するので、確認は仕事と仕事のあいだ、列を空にした最後に行う。

この処理は Pi の内部のテーブルに書き込む。
Pi Durable の版を固定し、処理を1つのモジュールにまとめ、Pi を上げるたびに削除のテストを流す。

### アーカイブの索引

アーカイブした範囲ごとに、検索の索引を R2 のエントリの隣に置く。

- `.index.json` は削除の処理のコードが書く。ユーザーとアシスタントのメッセージの本文、ツールの名前と引数、各ツールの結果の先頭 2,000 文字を、約 2,000 文字ずつの断片に分ける。断片ごとに、エントリの範囲と `.jsonl` の中でのバイトの範囲を持つ。正規化した語（検索用の文字列の関数で作る）ごとに、その語を含む断片を並べる。作ったときの `search_version` も記録する。
- `.summary.json` は `record_archive` の仕事が書く。要約と、その正規化した語を持つ。書いたら目録の行の `has_summary` を立てる。
- D1 の `archive_segments` の行が目録である。範囲、時刻、大きさ、SHA-256、抽出と要約が済んだかを持つ。範囲ごとに1行の小さな行である。
- オブジェクトと行は、運用者の保持期間の操作で一緒に消すときだけ消す。統合が期限切れにすることはない。

`history_search(query, before?)` は次のように動く。

1. このエージェントの目録の行を、新しい順に並べる。`before` があれば、それより前から始める。
2. その順に `.summary.json` と `.index.json` を、合わせて 4 MB を読むまで読む。
3. 問い合わせのすべての語を含む断片を当たりとする。[問い合わせ](#問い合わせ)と同じく、まず結合した語で、次に元の区切りで、最後に結合した語の前方一致で探す。要約も同じ方法で当てる。当たりは新しい順に、5件まで返す。
4. 当たったバイトの範囲を `.jsonl` から読み、エントリの ID と時刻と一緒に返す。探した中でいちばん古い時刻も返す。モデルはその時刻を `before` に渡して、さらに前を探せる。

## スキル

スキルは Agent Skills の形式に従う。
`name` と `description` を持つ `SKILL.md` と、必要なら `references/`、`assets/`、`scripts/` を入れたディレクトリである。

### 範囲と見える範囲

| 範囲              | 見えるエージェント                             | 変えるもの                           |
| ----------------- | ---------------------------------------------- | ------------------------------------ |
| `agent:<agentId>` | そのエージェント                               | 記憶係                               |
| `shared:<space>`  | `sharedSpaces` に `<space>` を含むエージェント | 記憶係（適用された提案を通してだけ） |

エージェントのスキルは、同じ名前の共有のスキルを隠す。
共有の範囲どうしでは、`sharedSpaces` で先に書いた範囲が勝つ。
一覧に同じ名前は1回しか出ない。

### 置き場所

- スキル1つが R2 のディレクトリ1つ（`skills/<scope>/<name>/`）にあたり、更新はその場で上書きする。`skills` の行には `content_sha256`（各パスとそのファイルの SHA-256 から作る）と `revision` を入れる。
- 更新は1つの操作で、途中で止まっても最後まで終えられるよう、ファイルを変える前に記録する。
  1. 新しいファイルを `skills/.blobs/<sha256>` に上げ、上書きするか消すファイルもそこに写す。中身のハッシュで置くので、同じファイルは1回しか置かれない。
  2. `op_id` と、変わるパスごとの変更前と変更後の SHA-256 を載せた `skill_writes` の行を `pending` で入れる。
  3. スキルのディレクトリのファイルを上書きし、消す。付属のファイルを先に、`SKILL.md` を最後に書く。
  4. 1つの `batch()` で、`content_sha256` を更新し（`WHERE revision = ?`）、ファイルごとのハッシュを載せた変更記録の行、`scope_revisions` の加算、`memory_ops` の行を書き、`skill_writes` の行を `done` にする。
- 記憶係は、起動したときと各仕事の前に、`pending` の `skill_writes` をすべて終わらせる。変更後の blob をディレクトリにもう一度写し、手順4を行う。手順3は何度行っても同じ中身を書くので、どこで止まっても新しい版で終わる。
- 巻き戻しは、変更記録の行の変更前の blob を同じやり方で書き戻す操作である。
- `skill_usage` は、スキルとエージェントの組ごとに使用回数を数える。仕事をするエージェントが upsert する。
- スキルのディレクトリと blob は `ARCHIVE` のバケットに置く。1つのスキルのファイルは32個まで、1つ 256 KB までとし、パスは `SKILL.md` か、`references/`、`assets/`、`scripts/` の下に限る。

### 一覧と読み込み

- `skills` 拡張が `skills` セクションを足し、見える有効なスキルを、名前、説明、パス `/skills/<scope>/<name>/SKILL.md` として並べる。並びは、エージェントのスキル、このエージェントの使用回数順の共有のスキル、全エージェントの使用回数順の共有のスキルの順で、最大50件とする。一覧は常に読み込む記憶と一緒に保存し、更新する。`SkillsEnv` が見せるスキルも、この保存した一覧で決まる。
- モデルは `@earendil-works/pi-durable/tools` の `read` ツールでスキルを読む。会話の `env` は `SkillsEnv` で、`/skills/<scope>/<name>/...` をそのスキルの R2 のディレクトリに対応させる読み取り専用の `ExecutionEnv` である。
- 見えないスキルのパスは not found を返す。書き込み、`exec`、`watch` は `not_supported` を返す。相対パスは `/skills` を基準に解決する。スクリプトは読めるが実行できない。
- `read` に付けた `afterTool` フックが、パスが `SKILL.md` で終わるとき、`skill_usage` を upsert する。

### 寿命の流れ

どの変更も、記憶係が `consolidate` か `apply_proposal` の中で操作として行い、`memory_ledger` に残す。

- **作る。** エージェントの軌跡の中で少なくとも2回成功した手順から、そのエージェントのスキルを作る。軌跡と失敗から学んだことを根拠に添える。記憶係が、そのエージェントの範囲の `consolidate` の仕事の中で `skill_write` で書く。書き込みは形を確かめ（frontmatter の `name` がスキルの名前と同じで、`description` が1〜1024文字であること、パス、大きさ）、`active` で保存する。再実行はしない。役に立たないスキルは使われずに stale になる。この仕事には `list_skills`、`read_skill`、`skill_archive`（アーカイブと復元）もある。
- **エージェントのスキルを更新する。** 同じエージェントの新しい根拠から、チェックを通して上書きする。
- **共有に上げる。** 2つ以上のエージェントのスキルが同じ手順を表しているとき、記憶係はまとめたスキルを上げ、元のスキルを並べた `shared_proposals` の行（対象は `skill`）を1つ作る。共有の範囲は、元のエージェントがすべて読む範囲を優先する。適用されたら、記憶係は `shared:<space>/<name>` を書き、`skill_usage` の行を移す。そのあと元のエージェントごとに、そのエージェントの `sharedSpaces` で名前を解決する。結果が新しい共有のスキルになるときだけ、元のスキルを `absorbed_into` 付きでアーカイブする。そうでなければエージェントのスキルを残し、理由を変更記録に書く。
- **共有のスキルを更新する。** 2つ以上のエージェントのスキル（たとえばそれぞれの上書き）を根拠にした提案が、チェックで受理され、適用されたときだけ行う。
- **上書きする。** 共有のスキルがあるエージェントで失敗し続け、別の手順なら成功するとき、記憶係は同じ名前のエージェントのスキルを、`based_on` に共有のスキルとその内容のハッシュを入れて書く。これはそのエージェントに対してだけ共有のスキルを隠す。いくつものエージェントが同じように上書きしたら、共有のスキルを更新する提案にする。
- **片付ける。** エージェントのスキルは、そのエージェントが14日使わなければ `stale`、30日で `archived` にする。共有のスキルは、どのエージェントも30日使わなければ `stale`、60日で `archived` にする。固定したものは対象外とし、アーカイブしたものは元に戻せる。日数は、最後に使われたときか、最後に内容を書いたとき（`updated_at`）から数える。復元以外の状態の変更では `updated_at` を変えない。

### 提案

変更を人が承認したりレビューしたりすることはない。
記憶係が提案を書いた時点でコードがチェックし、受理された提案は記憶係が自分で適用する。

- 提案は、`target_key`、書いたときの対象の `base_revision`、具体的な操作の payload（記録の内容か、blob として R2 に上げ済みのスキルのファイル）を持つ。適用されるのは、チェックしたものそのものである。
- チェックはその場で決め、`decided_by` に規則の版（`checks:1`）を残す。
  - 共有の範囲に新しく入る記録やスキルは、根拠のうちに、少なくとも2つのエージェントの有効な記録かスキルが要る。1つのエージェントの癖や、1つの汚染された会話ではないことの、独立した根拠にするためである。
  - 共有の範囲の中の整理（その範囲の記録をまとめる、置き換える）は、根拠がすべてその範囲の有効な記録であることが要る。
  - `required` には、2つのエージェントの記録か、すでに `required` である根拠が要る。
  - 記録の文が、従うべき指示として読めてはならない。秘密情報は提案の前に伏せる。
    通らなかった提案は理由付きの `rejected` として残り、ツールが記憶係に理由を返す。通った提案は `accepted` として残る。
- `accepted` は「受け入れたがまだ適用していない」を表すので、行そのものが消えない未処理の仕事になる。記憶係は仕事と仕事のあいだに、`accepted` の行すべてについて `apply_proposal` を列に入れる。いま走っている仕事が書いた提案は、その仕事のすぐあとに適用される。途中で止まっても、適用が遅れるだけである。
- `apply_proposal` はコードで行い、提案の ID を `op_id` にする。`applied` の行ならすぐ戻る。対象の revision が `base_revision` と違えば、行を理由付きの `conflict` にし、記憶係が今の revision に対して新しい提案を書くことがある。そうでなければ、1つの `batch()` で payload を適用し、`applied` と `applied_at`、変更記録の行、`scope_revisions`、`memory_ops` の行を書く。
- 提案、判断、適用はすべて変更記録に残り、スキルの変更はそこから巻き戻せる。

## 共有の記憶

- 記憶係は、複数のエージェントが頼っているエージェント範囲の記録から、`shared_proposals` の行を作る。コードがその場で受理か却下かを決める（[提案](#提案)を参照）。
- エージェントが読むのは、`sharedSpaces` に並べた共有の範囲である。小文字、数字、ハイフンからなる重複のない名前を8つまで並べられる。エージェントのストレージの `kodama:shared-spaces` に、Pi が持つ設定と並べて保存する。`setConfig` は保存するときに、常に読み込む記憶とスキルの一覧を更新する。
- 記憶係は、`consolidate` の仕事の中で `shared_propose` を使って提案する。提案できるのは、記録（新しいもの、または共有の記録を置き換えるもの）か、仕事の範囲のエージェントのスキルである。スキルのファイルは blob として保存するので、適用されるのはチェックしたものそのものである。共有の範囲の `consolidate` の仕事は、直接は何も変えず、提案だけを作る。
- エージェントの記録は、`memory_write` の `overrides` で共有の記録を上書きする。統合は、`required` の共有の記録を上書きしようとするエージェントの記録を無効にする。
- 適用された提案は、新しい記録になる。共有の記録をその場で書き換えることはしない。
- 信頼できない出どころから来た内容は、出どころ付きの `event` として残す。1つのエージェントの会話だけで、共有の範囲に届くことはない。
- 秘密情報は、書く前に伏せる。

## 進め方

どの段階でも、モデルをモックした workerd の結合テストを一緒に入れる。
障害のテストは、差し込んだフックから例外を投げて手順を止め、DO を開き直して確かめる。

1. **計測。**
   進捗の間隔を明示し、1ターンあたりの書き込み行数、DB の大きさ、文脈の大きさを記録する。
   テスト：1ターンあたりの行数が記録した予算を超えないこと。
2. **D1 の記憶と記憶係。**
   マイグレーション、検索用の文字列の関数、操作、仕事を処理する係を持つ `MemoryAgent`、`remember`、チェックポイント付きの `extract`、`memory_search`、revision 付きの常に読み込むセクション、`AlarmSchedule` を入れる。
   テスト：
   - `remember` が同じターンの中で `accepted` を返し、仕事が `persisted` で片づくこと。
   - ツールの呼び出しを繰り返しても2つ目の仕事ができないこと。
   - エージェントの判断による重複が断られること。
   - 仕事をするエージェントが記憶を書くツールを持たず、`AgentService` から記憶係に届かないこと。
   - 同じ置き換えを2回適用しても、有効な記録が1つ残り、内容が変わらないこと。
   - 古い revision を前提にした操作が `conflict` を返し、何も変えないこと。
   - 仕事 A の処理中に入れた仕事 B が、A の完了で reset されず、A の文脈も見ないこと。
   - 新しい訂正のあとで古い範囲を抽出しても、訂正が取り消されないこと。
   - `memoryChanged` を落としても、revision を確かめる間隔のあとの次のターンまでに写しが更新されること。
   - 抽出、復旧、削除のアラームが共存し、復旧の時刻を消してもほかが残ること。
   - 何度か compaction を経る前に話した事実があとで見つかること。
   - 再開した抽出が重複して書かないこと。
   - 失敗した抽出がチェックポイントを進めず、会話に影響しないこと。
   - 「使う」「リポ」「サーバレス」のような日本語の問い合わせが目当ての記録に当たること。
3. **古い行の削除。**
   R2 への書き出し、マニフェスト、索引、`prune_runs`、アーカイブの目録、削除のモジュール、`record_archive`、`history_search`、上限の閾値を入れる。
   テスト：
   - 消したあとも、会話が続き、もう一度 compaction でき、追い出しとアラームからの復旧ができ、取り消しもできること。
   - `snapshot()` が変わらないこと。
   - 残す期間の中のリクエスト ID は重複が排除されること。
   - 背景の compaction が生きているあいだは、エントリを消さないこと。
   - R2 への書き出しのあと、索引の前で止めても何も消えず、実行が続きから再開すること。
   - 索引のあとで止めても、再開して1回だけ消すこと。
   - 要約に入らず生のエントリにだけある語で、`history_search` が元のエントリを見つけること。
   - 読み取りの上限で探し終えたときに、探した中でいちばん古い時刻を返し、それを `before` に渡すとさらに前を探せること。
   - 記憶係を止めても保存領域を回収でき、あとで抽出が R2 の範囲から読むこと。
   - 上限の閾値を超えると、新しい入力がやり直せるエラーで断られること。
   - `databaseSize` が減ること。
4. **スキル。**
   blob、`skill_writes`、`skills` 拡張、`SkillsEnv`、`skill_usage` のフック、エージェントのスキルの寿命の流れ、片付けを入れる。
   テスト：
   - セクションが見える有効なスキルをパス付きで、エージェントのスキルを先に並べること。
   - エージェントのスキルが同じ名前の共有のスキルを隠すこと。
   - `read` が `SKILL.md` と、相対パスで指した付属のファイルを返すこと。
   - 見えないスキルのパスが not found になること。
   - `SkillsEnv` での書き込みと `exec` が失敗すること。
   - 更新の各ファイルを書いた直後で止めても、再起動で最後まで終わり、スキルが新しい版になり、`content_sha256` がファイルと合い、更新が `done` になること。
   - 変更記録の1行を巻き戻すと、変更前のファイルに戻ること。
   - `SKILL.md` を読むと `skill_usage` が upsert されること。
   - `SkillsEnv` が相対パスと `..` を `/skills` の中で解決すること。`registerEnvConformance()` には読み取り専用の形が無いので、読み取りの振る舞いをテストで直接確かめる。
5. **共有の記憶と共有のスキル。**
   `sharedSpaces`、範囲の優先、共有の記録、スキルを共有に上げることと上書き、提案のチェック、`apply_proposal` を入れる。
   テスト：
   - エージェントに見えるのが `sharedSpaces` の共有の範囲だけであること。
   - 共有の記録を `overrides` で指したエージェントの記録が、そのエージェントでだけ共有の記録の代わりになること。
   - 必須の共有の記録は読み込まれ続け、それを指したエージェントの記録は読み込まれないこと。
   - 同じ手順を持つ2つのエージェントから、共有に上げる提案が1つだけできること。
   - それを適用すると、共有のスキルができ、使用回数が移り、名前が新しい共有のスキルに解決される元のスキルだけがアーカイブされること。
   - 違う共有の範囲にいるエージェントのスキルを共有に上げても、各エージェントが前と同じ手順を選べること。
   - 1つのエージェントだけの記録やスキル、2つのエージェントの根拠がない `required` の記録、指示として読める文が却下されること。
   - 受理された提案が、それを書いた仕事のあとに、ちょうど1回適用されること。
   - 古い revision に対する提案が `conflict` になり、新しい変更を取り消さないこと。
   - 退けた提案は何も変えないこと。
   - 共有のスキルが、適用された提案を通してしか変わらないこと。
6. **評価。**
   compaction と古い行の削除のあとに、確認の質問をする。事実の想起、触ったファイル、続きから再開できるか、決定の理由、知識の更新、時間に関する質問、答えないべきときに答えないかを確かめる。
   `test/evaluation.test.ts` は、削除と DO の追い出しのあとに、台本どおりに答えるモデルでこれを流す。決定は常に読み込む記憶に、最初のほうのターンは要約にある。`history_search` は消したエントリにしかない語を見つける。置き換えた決定は、いちばん新しい memory セクションに新しいものだけを残す。知らない話題は何も見つからない。アーカイブより古い `before` では何も見つからない。消した範囲のリクエスト ID でやり直すと、最初の受付が返る。
   台本どおりのモデルなので、確かめているのは文脈に何が届くかであり、モデルがそれをうまく使うかではない。触ったファイルと続きからの再開は、本物のモデルで確かめる必要がある。

## 設計の理由

ここでは、既存のシステムと論文から何を借り、何を退けて今の構成にしたかを、判断ごとに残す。
各判断の「理由」には、外の根拠（既存のシステムか論文）があるものと、kodama の事情だけで決めたものがある。
後者には「kodama の事情」と書く。

### 前提

- **Pi Durable はエントリを消さない。**
  仕様書には「head は以後の文脈を変えるだけで、古いエントリをストレージから消さない」とある（Pi Durable spec §2.1）。
  compaction も `reset()` も、モデルに見せる範囲の先頭を動かすだけである。
  終わったタスクの記録や、セクションが変わったときの記録も残り続け、Pi にはこれらを削る公開の API が無い。
- **文脈はすでに縮められる。**
  Pi Durable の compaction は既定で動く（`reserveTokens` 16384、`keepRecentTokens` 20000、`backgroundTokens` 32768）。
  要約は構造化したチェックポイントの形式で作られ、前回の要約を引き継ぐ（spec §8.7）。
- **DO の上限は 10 GB である。**
  上限に達すると、書き込みは `SQLITE_FULL` で失敗し、読み取りと削除だけが通る（Durable Objects FAQ）。
  エージェントとしては動けなくなる。
- **要約にすべては残らない。**
  圧縮のたびに、まれな細部が黙って捨てられる（要約ドリフト、2603.07670）。
  原文を残して検索で戻せる方式は、どの圧縮頻度でも再現率が 0.95 前後だった。
  要約で上書きする方式は 0.33〜0.56 で、圧縮の頻度が高いほど悪かった（2607.08032、小規模な実験）。
- **終わらない1セッションは学習にも悪い。**
  Hermes Agent のドキュメントは、リセットしないと1つのセッションが何週間も続き、compaction が伸び続ける履歴に繰り返し走って高くつき、学習のループがほとんど回らないと書いている。
  同じ会話を担当し続ける kodama の使い方は、まさにこの状況にあたる。

スキルは、名前と説明だけをプロンプトに載せ、本体は関係するときに読み込む（Anthropic の progressive disclosure）。

### 1. 長期記憶はエージェントの DO の外（D1 と R2）に置く

**決めたこと。**
Pi のセッションは DO に残し、長期記憶は D1、消す前の生の記録とスキルのファイルは R2 に置く。

**理由。**

- サーベイは、文脈に作業中の記憶を置き、長期の記録を外の保存先に置く形（Pattern B）から始めて計測することを勧めている（2603.07670）。
  OpenClaw も Hermes も、長期記憶を会話の記録とは別のファイルに持つ。
- 費用で大きいのは書き込みの量と稼働時間であり、保存しているバイト数ではない（下の見積もり）。
  1行あたりや 1 GB あたりでは、DO は D1 より高くない。
  それでも外に置くのは、kodama の事情として次の3つがあるからである。
  - 長期記憶はエージェントの間で共有したい。
  - UI や整理の処理が、エージェントの DO を起こさずに長期記憶を読めるようにしたい。
  - セッション自身の行は、時間とともに消していく。
- D1 は FTS5 と、`batch()` によるトランザクションを持つ。
  R2 は、1 GB あたり D1 の50分の1の値段で大きなものを置ける。

費用の見積もりは次のとおりである。
価格は Cloudflare の料金ページ（Workers Paid、2026年10月時点）から取った。
無料枠はアカウント全体で1か月あたりの量である。

| 項目                        | 価格                                                          | 無料枠     |
| --------------------------- | ------------------------------------------------------------- | ---------- |
| DO の稼働時間               | 100万 GB 秒あたり 12.50 ドル。動いている間、128 MB 分で数える | 40万 GB 秒 |
| DO または D1 の行の書き込み | 100万行あたり 1.00 ドル（削除も数える）                       | 5,000万行  |
| DO または D1 の行の読み取り | 100万行あたり 0.001 ドル                                      | 250億行    |
| DO の SQLite の保存量       | 1 GB 月あたり 0.20 ドル                                       | 5 GB       |
| D1 の保存量                 | 1 GB 月あたり 0.75 ドル                                       | 5 GB       |
| R2 Standard の保存量        | 1 GB 月あたり 0.015 ドル                                      | なし       |
| R2 の書き込みと読み取り     | 100万回あたり 4.50 ドルと 0.36 ドル                           | なし       |

| ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | --------------------------------- |

| `subscribe()` のストリームを1日中開けておく（ハイバネーションしない）                                                     | 32万4,000 GB 秒、4.05 ドル                  | 誰も見ていないストリームを閉じる  |

**採らなかった案。**

- **すべてを DO に置く**（エージェントごとと共有の範囲ごとに記憶用の DO を作る）。
  Cloudflare Agent Memory は記憶のプロファイルごとに DO を使っているので、成り立つ形ではある。
  しかし共有の記憶には別の DO が要り、UI や整理の処理が読むたびにその DO を起こすことになる。
- **記憶を R2 の markdown ファイルだけで持つ**（OpenClaw や Hermes がディスクに置くのと同じ形）。
  保存はいちばん安く、人が手で直しやすい。
  しかし検索には別の索引が要り、R2 にはトランザクションが無い。
- **Cloudflare Agent Memory を使う。**
  この設計とよく似ていて、`cf` にはすでに `agentMemory` のバインディングがある。
  ただし非公開ベータなので、記憶の保存先はインタフェースの裏に隠し、あとで差し替えられるようにする。

### 2. compaction は Pi に任せる

**決めたこと。**
Pi の組み込みの compaction を既定のまま使い、フックも置き換えもしない。

**理由。**

- Pi はすでに、切れ目を選び、構造化した形式で要約し、前回の要約を引き継ぎ、失敗したらやり直し、文脈があふれたときにも立て直す。
- 自前の要約が効くという根拠は、別の場面のもの（ACE、2510.04618 が書き直すのは会話ではなく手引き）か、ベンダー自身の測定（Factory の anchored iterative summarization）である。
- 要約を自前で持つと、そのプロンプト、失敗、劣化まで kodama が背負うことになるが、得られるものははっきりしない。
- 要約の弱さ（前提の「要約にすべては残らない」）は、要約を良くするのではなく、事実と生の記録を要約の外に持つことで補う（判断3と判断6）。

**採らなかった案。**

- **`beforeCompact` フックで記憶を抽出し、足し込み式の要約を返す。**
  記憶が Pi の compaction の処理に縛られ、Pi の要約が問題だという根拠も無いまま、要約の質を kodama が背負うことになる。
  評価の確認質問で、記憶と `history_search` では補えない取りこぼしが見えたときのために、選択肢として残す。
- **観測マスク**（古いツール出力を伏せる。2508.21433 では費用を半分にしつつ同等の成績）。
  同じ種類の最適化なので、ツール出力が文脈の大半を占めると測れてから考える。

### 3. 生の記録は R2 に残し、DO からは古い行を消す

**決めたこと。**
compaction で文脈の外に出たエントリを R2 に書き出して確かめ、コードで R2 に索引を、D1 に目録を作ってから、DO の行を消す。
要約は、あとから記憶係が足す。
DO を丸ごと消すことはしない。

**理由。**

- 検索で戻せる圧縮は、要約で上書きするだけの圧縮より強い（2607.08032）。
  OpenClaw も Hermes も Cloudflare Agent Memory も、生の履歴を残している。
  よく使う保存領域から消すのはかまわないが、唯一の写しを消してはいけない。
- OpenClaw は `session.maintenance` で古いセッションを整理し（既定は30日、5,000行）、Hermes は終わったセッションを `prune` で消す。
  消す処理を持つこと自体は既存のシステムでも普通である。
- kodama では compaction は保存領域から何も消さないので、消すのは別の処理にするしかない。
  workerd での実験で、境目より前のエントリと終わったタスクを消しても会話が続き、要約が送られ、`snapshot()` が変わらず、古いリクエスト ID の重複排除も効くことを確かめた。
- 要約だけでなく、生のエントリも索引にする。
  あとで探し直したくなるのは、エラーコードのように、要約と抽出から落ちたものであることが多い（要約ドリフト、2603.07670）。
  要約に頼る索引では、そこに届かない。

**採らなかった案。**

- **古い行を消さない。**
  いちばん簡単で、テキストの会話だけなら 10 GB はかなり遠い。
  しかし上限に当たると止まる。
  段階1と2はこの形のままでも動くので、消す処理は計測の結果を見てから入れてもよい。
- **DO を丸ごと消し、引き継ぎメモから始め直す。**
  Pi の公開の API（`reset()` と `deleteAll()`）だけで済み、Hermes が圧縮のたびに続きのセッションを作るのに近い。
  しかし会話の続きが途切れ、マニフェストから戻す処理と世代の番号が要り、購読している人もみな切れる。
  Pi の変更で古い行を消す処理が危うくなったときの、代わりの手段として残す。
- **要約だけを記憶の記録として索引にする**（この計画の前の版）。
  要約に無い語には届かず、`event` として扱うと、R2 のオブジェクトが残っているのに索引だけが期限切れになりうる。
- **Pi Durable に公式の削除の API ができるのを待つ。**
  本来はこれがいちばん良い。
  Pi は自分の前提（エントリは不変で ID は使い回さない、fork は親を読む）を知っている。
  上流に提案する価値はあるが、待つほどではないので、消す処理は1つのモジュールにまとめて差し替えられるようにする。

### 4. 記憶を書くのは専用の記憶係だけにする

**決めたこと。**
長期記憶を書くのは記憶係（`MemoryAgent`）だけにする。
仕事をするエージェントが持つのは、検索のツールと `remember` だけである。

**理由。**

- Letta は、記憶の編集を会話するエージェントから外し、sleep-time エージェントに移した。
  記憶の管理と会話を1つのエージェントにまとめると、遅くなり（会話中に記憶の操作を呼ぶ）、信頼性も落ちる（記憶のツールと普通のツールの両方を呼ぶ）からである。
- Cloudflare Agent Memory は、モデルに保存先をそのまま触らせる方式を「本来の作業ではなく、保存と検索の戦略にトークンを使う」と書いている。
- Hermes は、記憶の見直しを主のモデルより安いモデルで走らせられる。
  記憶係のモデルを別に選べるのも同じ考えである。
- 共有ブロックを複数のエージェントが同時に丸ごと書き直すと、更新が失われる（Letta）。
  書き手が1人なら、範囲ごとの書き手が1人に決まり、この問題が起きない。
- sleep-time compute（2504.13171）は、待ち時間に前もって計算しておくと、応答時の計算を減らせることを示している。

**採らなかった案。**

- **仕事をするエージェントが自分で記憶を書く。**
  すべてのリクエストに記憶のツールと指示が載り、仕事用のモデルを記録の管理に使い、1つの範囲に書き手が何人もいることになる。
  Letta がやめた形と同じである。

### 5. 記憶係は `Agent` を継承した内部専用の DO にする

**決めたこと。**
`class MemoryAgent extends Agent` を別のクラスとして公開し、`MEMORY_AGENT` のバインディングでだけ呼ぶ。
`Agent` を基本的にそのまま継承し、仕事の列を素通りするメソッドだけが例外を投げる。
今のところ `AgentService` からは届かない。

**理由（kodama の事情）。**

- `Agent` と Pi Durable は、永続的な受け付け、リクエスト ID による重複の排除、順に処理する受付の列、復旧をすでに持っている。
  記憶係は、モデルを使う部分にこれらを使い、その手前に kodama の仕事の列を置く（判断14）。
- 継承したクラスに別のバインディングを持たせると、公開の RPC から届かないことと、ツールが別の登録表にあることが、どちらも構造で保証される。
- `subscribe` と `snapshot` を継承すれば、記憶係の処理もほかのエージェントと同じように見られる。あとで UI に出すときに、エージェント側のコードを足さずに済む。

**採らなかった案。**

- **記憶係を Cloudflare Workflow にする。**
  Workflows はモデルを待つあいだ課金されないが、`Agent` がすでに持つものを、別の実行の仕組み、別のツール、別のテストで作り直すことになる。
  節約できる稼働時間も小さい（判断1の見積もりで、待ち時間の稼働は月 1.35 ドル）。
- **公開の名前空間にある、予約した ID の `Agent` にする。**
  公開の RPC のすべてのメソッドでその ID を弾く必要があり、ツールの制限も設定の検査に頼ることになる。

### 6. 書き込みは、その場の `remember`、アイドル時の抽出、毎日の統合の3つ

**決めたこと。**

- ユーザーが頼んだときと、エージェントが残すべきと判断したときは、そのターンの中で `remember` を呼び、記憶係が次の仕事として処理する。
- エージェントがしばらくアイドルになったときと、古い行の削除がチェックポイントの遅れを見つけたときに、会話の記録から抽出する。すでに消した範囲は R2 から読む。
- 1日1回、統合する。

**理由。**

- 既存のシステムは、どれもこの3種類のどれかを持っている。

  | きっかけ         | 既存のシステム                                                                                                                          |
  | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
  | その場で明示的に | Cloudflare Agent Memory の `remember`、Hermes と OpenClaw の memory ツール                                                              |
  | 裏で会話から     | Grok Build（ターンが終わるたび）、Hermes（ターン後の見直し）、Cloudflare Agent Memory（compaction の時点）、OpenClaw（compaction の前） |
  | 定期的にまとめて | OpenClaw の dreaming、Grok Build の `/dream`、Devin の dreaming（1日1回ほど）                                                           |

- 抽出は compaction からではなく、会話の記録から行う。
  OpenClaw が compaction の直前に記憶を書き出すのは、文脈がエージェントの見る唯一の場所だからである。
  kodama では compaction は保存領域から何も消さないので、エントリは消すまで `scanEntries` で読める。
- 記憶システムの誤りは、抽出と更新の段階で生まれて溜まる（HaluMem、2511.03506）。
  過去の誤りが次の誤りを呼ぶ（2505.16067 の error propagation）。
  そのため抽出した候補は、根拠のエントリと突き合わせて裏付けのないものを捨て、出どころを付けて保存する。
- エージェントの判断による保存は、頼まれた保存より弱く扱う（重要度を低めにし、重複や価値の低いものは断り、使われなければアーカイブする）。
  Hermes も、頼まれずに会話の中で出ただけの事実は記憶しない。
  ふつうの利用者でも記憶に細工できる（MINJA、2503.03704）ので、頼まれていない保存を無条件に受け入れない。

### 7. 記憶は4つの種類に分け、事実は置き換え、出来事は薄れさせる

**決めたこと。**
`fact`、`instruction`、`event`、`task` に分ける。
新しい `fact` や `instruction` は、検索で見つけた古い記録の ID を指して置き換える。
`event` は新しさで順位を下げる。

**理由。**

- 4つの種類と、古い記録を消さずに `superseded` にする置き換えは、Cloudflare Agent Memory と同じである。
- Mem0（2504.19413）は、似た記憶を引いてから、候補ごとに ADD、UPDATE、DELETE、NOOP を選ぶ。
  抽出の手順4（追加、置き換え、無効化、何もしない）はこれに当たり、置き換える相手を ID で指すのも同じである。
- 事実に時間の減衰をかけるのは種類の取り違えである（2604.11364）。
  Zep（2501.13956）は、古くなった事実を辺の無効化で扱う。
  出来事には新しさの減衰が効く（Generative Agents、2304.03442 の減衰係数 0.995）。
- モデルは古くなった事実をそのまま受け入れがちである（STALE、2605.06527 で正答率 55.2%）。
  置き換えは明示的に記録する。

**採らなかった案。**

- **話題キーを持つ**（Cloudflare Agent Memory は事実と指示に正規化した話題キーを付け、同じキーの新しい記憶が古いものを置き換える）。
  キーがあれば、話題ごとに有効な記録を1つに保つことをデータベースで守れる。
  ただしそれは、モデルが同じ話題にいつも同じキーを作るときだけである。
  キーがぶれると置き換えが黙って効かなくなり、キーが粗すぎると関係のない事実を置き換えてしまう。
  書き手が1人で仕事も1件ずつなので、データベースでの保証は要らず、言い換えによる重複は統合がまとめる。
- **人ごとの範囲を持つ**（Hermes の Honcho は相手ごとに別の peer プロファイルを持つ）。
  kodama の事情として、相手の記憶は要らないと決めた。

### 8. 常に読み込む記憶は小さく固定し、区切りでだけ変える

**決めたこと。**
常に読み込む記憶は、エージェント分 2,200 文字、共有分 1,000 文字に収める。
DO に写しを置き、アイドルのあいだに、起動時、変更の通知、ターンの前に `scope_revisions` が新しくなっていたときに更新する。

**理由。**

- Hermes の `MEMORY.md` は 2,200 字で、セッション開始時に固定する。
  固定するのは、プロンプトのキャッシュを効かせるためである。
- Pi は、セクションが変わるとそれを新しいシステムエントリとして送り直す。
  ターンの途中で変えると、そのたびに書き込みとキャッシュの取り直しが起きる。
- 予算の使用量を表示する形（`[67% — 1,474/2,200 chars]`）は Hermes と同じである。
- 記憶係が D1 に書いたあと、知らせる前に止まると、知らせは失われる。
  変更と同じ `batch()` で revision を進めれば、各エージェントが自分で変更に気づける。
  記憶係が全エージェントを起こす必要もない（kodama の事情）。

### 9. 検索は D1 の FTS5 と Intl.Segmenter で始める

**決めたこと。**
`Intl.Segmenter` で語に分けた文字列を FTS5（`unicode61 remove_diacritics 2`）で索引にし、BM25 で並べてから新しさと重要度で並べ直す。
アーカイブしたエントリの生の本文は、同じ語で範囲ごとの索引のファイルにして R2 に置き、新しい順に上限まで読む。
ベクトル検索は最初の版には入れない。

**理由。**

- Hermes の `session_search` は SQLite FTS5 である。
  OpenClaw の組み込みの検索も SQLite の BM25 から始まり、ベクトルは埋め込みの提供元を設定したときだけ足される。
- サーベイは、単純な形から始めて計測することを勧めている（2603.07670）。
- D1 で FTS5 と `Intl.Segmenter` を組み合わせて日本語の全文検索を作った例がある（zenn、coji）。
- `Intl.Segmenter` が workerd でも Node と同じ結果になることを確かめた。
  「使う」「リポジトリ」「リポ」「デプ」「マネージャー」「レビュー」「サーバレス」と「サーバーレス」「ベストプラクティス」「ＰＮＰＭ 使う」は当たった。

- アーカイブの索引は、索引の対象のエントリの隣の R2 に置く（kodama の事情）。
  索引は会話の記録とツールの出力に比例して大きくなるが、D1 は全エージェントで1つ、上限 10 GB で、1 GB あたりの値段も R2 の50倍である。
  R2 なら索引とエントリを一緒に残して一緒に消せ、作るときに D1 のバッチの制限も受けない。

**採らなかった案。**

- **FTS5 の trigram のトークナイザを使う。**
  trigram は3文字以上の問い合わせが要るので、「使う」や「リポ」のような2文字の語が引けない。
  索引も文字の位置ごとに作るので大きくなる。
  `unicode61` だけでは、空白の無い日本語の文が丸ごと1語になる。
- **最初からベクトルと RRF を入れる**（Cloudflare Agent Memory、OpenClaw のハイブリッド検索）。
  まず全文検索で始め、取りこぼしを計測してから、ベクトルを足すかを決める。
- **アーカイブの索引を D1 の FTS5 にする**（この計画の前の版）。
  アーカイブ全体を1つの順位で並べられるが、索引がすぐに共有の D1 の大半を占めてしまう。

### 10. 手順はスキルにし、Pi の標準の読み方で読ませる

**決めたこと。**
スキルは Agent Skills の形式で R2 に置く。
一覧は `skills` セクションに名前、説明、パスで出し、本体はモデルが Pi の `read` ツールで読む。
`read` が読む先は、R2 に対応させた読み取り専用の `ExecutionEnv`（`SkillsEnv`）である。

**理由。**

- どの既存のシステムも、手順は事実と分けてスキルとして持ち、名前と説明だけを先に見せる（Anthropic の progressive disclosure）。
- Claude Code は「複数の手順からなる内容は、スキルに移す」と書いている。
- Pi のスキルも、名前と説明を一覧に出し、本体はモデルが `read` で読む。
  同じ読み方にしておけば、付属のファイルを相対パスで指すスキルがそのまま動く。

**採らなかった案。**

- **スキル専用のツールを作る**（`skill_load` と `skill_search`）。
  Pi の `read` ツールと役割が重なり、付属のファイルを相対パスで指すスキルが動かなくなる。

### 11. スキルは検証できた経験からだけ作り、少なく保つ

**決めたこと。**
少なくとも2回成功した手順からだけ作り、チェックを通ったら有効にする。
一覧は最大50件にし、使われないスキルは stale にしてからアーカイブする。

**理由。**

- 成功して検証できた軌跡から作ったスキルは効いた。
  AWM（2409.07429）で相対 24.6% と 51.1%、ASI（2504.06821）で 23.5%（検証の仕組みが効いたと書いている）。
  ReasoningBank（2509.25140）は、成功だけでなく失敗からも教訓を取り出す。
- 作業の前にエージェント自身が書いたスキルは、スキル無しより 8.1〜11.5 ポイント悪かった（SkillsBench、2602.12670）。
  同じ論文で、3つ以下の部品に絞ったスキルは大きな束より良かった。
- 更新を重ねると、その回だけの事情が混ざって散らかる（SkillEvolBench、2605.24117）。
- 一覧から選ぶ精度は、16〜32個で 96〜98%、64個で 92%、128個で 78% と落ちる（2607.10113）。
  50件の上限はこの数字から取った。
- Hermes の curator は、14日使われなければ stale、30日でアーカイブし、自動では消さず、固定したものは対象外にする。
  統合でまとめたスキルには `absorbed_into` を付ける。
  エージェントのスキルの数字と `absorbed_into` はこれに合わせた。

### 12. スキルはエージェント固有と共有の2つの範囲に分ける

**決めたこと。**

- スキルの範囲は `agent:<agentId>` と `shared:<space>` の2つにし、エージェントが読む共有の範囲は `sharedSpaces` で決める。
- 同じ名前なら、エージェントのスキルが共有のスキルを隠す。
- スキルはまずエージェントのスキルとして生まれ、2つ以上のエージェントが同じ手順を持ったときに、チェックを通った提案で共有に上げる。
- 共有のスキルは、受け入れられた提案を通してしか変わらない。
- スキルはその場で上書きする。更新は、先にファイルごとの変更前と変更後のハッシュを記録し、途中で止まっても再起動で終える。変更記録に変更前のファイルを残し、巻き戻せるようにする。
- 共有のスキルの片付けは、どのエージェントも使わなくなってからにし、期間も長くする。

**理由。**

- 範囲の重ね方と隠し方は、既存のシステムと同じである。
  Hermes は、プロジェクト、ローカル、外部のディレクトリの順に優先し、同じ名前は優先度の高い方が隠して、隠した方を記録に残す。
  プロジェクトのスキルが同じ名前のスキルに勝つのは「その場所では持ち込んだスキルが勝つ」ためだと書いている。
  Pi も、同じ名前は先に見つけた方を使い、警告を出す。
  一覧に同じ名前が1回しか出ないのはこれに合わせた。
- 共有のスキルを書き手から守るのは、構造で行う。
  Hermes では、エージェントが作ったスキルはローカルに書かれるが、既存のスキルは見つかった場所で直接書き換えられる。
  ドキュメントも「外部のディレクトリは書き込みの防壁ではない」と書き、守りたければファイルの権限で分けるよう勧めている。
  kodama では、記憶係の `skill_write` がエージェントの範囲しか受け付けず、共有のスキルは `apply_proposal` でしか書かれない。
- 共有に上げるときに提案のチェックを挟むのは、共有の記憶と同じ理由である（判断13）。
  悪意ある「成功体験」を植え付けると長く残る（MemoryGraft、2512.16962）ので、共有のスキルはとくに危ない。
  Collaborative Memory（2505.18279）も、書き込みの方針で個別と共有のどちらに置くかを選び、出どころを変えられない属性として付ける。
- 2つ以上のエージェントで同じ手順が成功したことは、1つのエージェントの事情ではない根拠になる。
  これは判断11の「検証できた経験から作る」を、エージェントをまたいで当てはめたものである（kodama の事情）。
- 上書きと変更記録は Hermes と同じ形である。
  Hermes はスキルを見つかった場所でそのまま書き換え、版を並べて持たない。
  そのかわり、スキルへの変更をすべて追記だけの記録に残し、ファイルごとの変更前と変更後の SHA-256 を付け、中身はハッシュをキーにして重複なく保存する。
  1件の変更だけを巻き戻すことも、消したスキルを戻すこともできる。
  スキルは、Hermes や Pi と同じく、ただのディレクトリのままになる。
- ファイルに触る前に更新を記録するのは、途中の停止に備えるためである（kodama の事情）。
  記録が無いと、途中で止まったときに新旧が混ざったまま今のスキルとして残り、変更記録からもどこまで進んだかが分からない。
  変更後のファイルがすでに blob にあるので、更新を終えるのは何度繰り返してもよい写しになる。
- 共有に上げたあと元のスキルをアーカイブするのは、そのエージェントで名前を解決した結果が共有のスキルになるときだけである（kodama の事情）。
  エージェントによって読む共有の範囲は違い、先の範囲に同じ名前のスキルがあることもある。
  2つのエージェントで成功したことは、共有のスキルを提案する理由にはなるが、元の写しを消してよい理由にはならない。
- 共有のスキルを長めに残すのは、2つ以上のエージェントの根拠があり、使うエージェントが複数いるからである。
  Hermes の curator は、既定ではエージェントが作ったスキルしか片付けない。
  同梱のスキルが黙って消えると、壊れたように見えるからだと書いている。
  kodama は共有のスキルも片付けるが、期間を2倍にし、アーカイブしたものは戻せるようにする（kodama の事情）。
- エージェントごとの上書きは、Hermes のプロジェクトのスキルと同じく、その場所でだけ勝つ形である。
  上書きが何件も同じ方向に揃ったら、共有のスキルを直す根拠として提案に回す（kodama の事情）。

**採らなかった案。**

- **版ごとに R2 のディレクトリを分ける**（`skills/<scope>/<name>/v<version>/`）。
  変わらないファイルまで版ごとに写すことになる。
- **中身のハッシュで置いたファイルの、変えない manifest を切り替える。**
  読む側が新旧の混ざりを見ることはなくなるが、どの読み取りも manifest を通り、スキルを読むあいだは読み手が manifest を固定する必要がある。
  更新中の短い混ざりは受け入れる（根拠が弱いところを参照）。
- **ファイルをその場で上書きし、付属のファイルを先に、`SKILL.md` を最後に書く**（この計画の前の版）。
  途中で止まると、新旧が混ざったスキルが今のスキルとして残る。
- **共有のスキルだけにする**（全エージェントで1つの一覧を持つ）。
  1つのエージェントでしか成功していない手順が全員に配られ、判断11の根拠と合わない。
  一覧も全員分の数に膨らむ。
- **エージェントのスキルだけにする。**
  同じ手順を各エージェントがそれぞれ覚え直すことになり、改善も共有されない。

### 13. 共有の記憶はチェックを通った提案で書き、出どころを残す

**決めたこと。**
共有の範囲には、記憶係が作った提案がコードのチェックを通り、書いたときの revision に対して適用できたときだけ書く。
変更を人が承認したりレビューしたりすることはない。
共有の範囲に記録やスキルを新しく入れるには、根拠として少なくとも2つのエージェントの有効な記録かスキルが要る。範囲の中の整理には、根拠がすべてその範囲の記録であることが要る。
適用した提案は新しい記録になり、その場で書き換えない。
提案、判断、適用はすべて変更記録に残す。
秘密情報は書く前に伏せ、指示として読める文は却下する。

**理由。**

- kodama のエージェントは何か月も人の手を離れて動く。人を挟むと提案が待たされ、共有の記憶が古くなる。人による承認は設計に含めない（kodama の事情）。
- ふつうの利用者でもエージェントの記憶に細工できる（MINJA、2503.03704）。
- 既存のプロンプトインジェクション対策では、記憶の汚染を防げない（MPBench、2606.04329）。
- マルチエージェントの記憶でいちばん大きな課題は整合性であり、記憶への出入りを細かく制御する必要がある（2603.10062）。
- Collaborative Memory（2505.18279）は、個別と共有の2層に分け、読み書きの方針で見える範囲を決め、出どころを変えられない属性として残す。
  このチェックは、その書き込みの方針をコードで行うものである。
- OpenClaw は、信頼できない出どころの報告は、信頼できるレビュー役が確かめるまで記憶にしないと書いている。
  kodama にはレビュー役がいないので、代わりに2つ目のエージェントによる裏付けを求める。
  1つの汚染された会話や1つのエージェントの癖だけでは、全エージェントに届かない。
  スキルを共有に上げるときと同じ根拠の規則である（判断12）。
- Hermes は、記憶の書き込みをインジェクションと持ち出しの型で検査してから受け入れる。
- Cloudflare Agent Memory も、記憶のプロファイルを複数のエージェントと人で共有する形を示している。
  共有すること自体は普通の形である。
- 書き手が1人でも、古い変更は防げない。
  同じ revision に対して書いた2つの提案を順に適用すると、古い方が新しい方を取り消してしまう。
  適用のときに `base_revision` を照らせば、これは `conflict` になる（kodama の事情）。
- `accepted` と `applied` を分けると、受け入れた行そのものが未処理の仕事になる。
  判断と仕事の投入のあいだで止まっても、適用は失われない（kodama の事情）。

**採らなかった案。**

- **人による承認**（`AgentService` の `listProposals` と `decideProposal`）。
  提案が誰かを待ち続けることになり、エージェントが自分で動くという前提に合わない。
- **記憶係が共有の範囲に直接書く。**
  汚染されていてもいなくても、1つのエージェントの会話が2つ目の根拠なしに全エージェントへ届く。

### 14. 書き込み、仕事、古い行の削除は、やり直しと途中の停止に耐える

**決めたこと。**
書き込みはどれも、`op_id` と前提を持つ操作にする。
記憶係は自分の列の後ろで仕事を1件ずつ処理し、各仕事の前に reset する。
古い行の削除は、再開できる状態の遷移にし、最後の手順で短い排他の区間の中で条件を確かめ直す。

**理由。**

- `INSERT OR IGNORE` は、部分一意インデックスの違反も無視する。
  D1 の `batch()` が取り消すのは、文が失敗したときだけである。
  前の版の規則を最小の SQLite で動かすと、同じ置き換えを繰り返したときに今の記録が `superseded` になり、有効な記録が無くなった。
  変更の前に `memory_ops` を確かめ、バッチの中では普通の `INSERT` を使えば、繰り返しは何もせず、想定外の状態は取り消しになる。
- Pi Durable 1.2.0 の `reset()` は、reset が置かれたときではなく、受け付けられたときに戻る。
  列で待っている仕事は前の仕事の最後の区切りで始まり、次の `postTools` の区切りで reset が置かれると、理由 `reset` の `unanswered` で終わる（spec §6）。
  そのため、仕事のあとに reset すると次の仕事を切ってしまい、次の仕事が前の文脈を見ることもある。
  仕事を1件ずつにし、アイドルのあいだに reset を受け付ければ、Pi はそれをその場で、次の入力より前に置く。
- Pi のアイドルの待ちは背景のタスクを含まない。
  背景の compaction は、再開するときに記録した `tail` からエントリを読み直す（spec §8.7）。
  背景の compaction が生きているうちにエントリを消すと、それが要るものを消してしまう。
  最初に確かめた条件も R2 に書いているあいだに変わりうるので、消す直前にもう一度確かめる。
- `blockConcurrencyWhile` には30秒の制限があるので、R2 への転送は囲めない。
  中に入れるのは、ローカルでの確認と削除だけである。
- `sendMessage` が戻るのは受付が受け入れられたときで、記憶係が終わったときではない。
  そのため削除は、仕事が受け付けられたことではなく、自分のコードがアーカイブの索引と目録を書いたことを確かめてから行う。

**採らなかった案。**

- **`INSERT OR IGNORE` の対象を主キーだけに絞る**（`ON CONFLICT (id) DO NOTHING`）。
  取り消しの規則との矛盾は消えるが、繰り返したときに今の記録を無効にしてしまう問題は残る。
- **削除の実行全体を `blockConcurrencyWhile` で囲む。**
  R2 への転送がその制限を超えうる。

### 根拠が弱いところ

確定させる前に見ておくべき点である。

- **本番の `databaseSize` が古い行を消したあとに減るか**は確かめていない。
  ローカルでは 20.5 MB から 5.1 MB に減った。
- **`submissions` は消さない。** 入力1つにつき1行が、エージェントのあるかぎり残る。
- **1ターンで書く行数**は workerd で測った（`test/measurement.test.ts`、Pi Durable 1.2.0）。
  40回に分けて1秒かけて流す応答で、100 ms の間隔では約111行、1秒の間隔では約66行だった。
  進捗のコミット1回で約5行、それとは別に1ターンで約66行を書くことになる。
  本番の値は違うことがある。
- **日本語の検索の取りこぼし**として、「プラクティス」だけでは「ベストプラクティス」に当たらない。
- **途中の停止への備えは、Pi Durable 1.2.0 の仕様と SQLite で確かめただけで、workerd ではまだ動かしていない。**
  背景の compaction の確認と、止まった実行の再開は workerd で試した（`test/prune.test.ts`）。reset の順番と D1 の `batch()` の取り消しは、段階4の障害のテストで確かめる。
- **前の版の常に読み込む記憶が、会話の中に残る。**
  Pi は変わったセクションをメッセージとして足すので、compaction で消えるまで、モデルには古い版のあとに新しい版が見える。新しい版は最後にあり、更新だと示される。
- **スキルの更新の途中に読むと、更新が終わるまで新旧のファイルが混ざりうる。**
  更新は統合と `apply_proposal` の中でしか行わず、`SKILL.md` を最後に書くので、受け入れる（Hermes も同じ）。
- **`history_search` は索引のファイルを新しい順に上限まで読む**ので、全範囲を通した順位は無く、古いものを探すには `before` を使って何度か呼ぶことになる。1回で何範囲を探せるかは索引の大きさで決まり、まだ測っていない。
- **D1 は全エージェントで1つのデータベースで、上限は 10 GB である。**
  抽出した記録は小さいが、変更記録と提案が積み上がる。
  統合が大きさを記録するが、データベースをいつ分けるかは決めていない。
- **共有のスキルの片付けの期間（30日と60日）、共有に上げるのに要るエージェントの数（2）、一覧の上限（50）**は、外の根拠をそのまま使ったものではない。
  50は 2607.10113 の数字から余裕を取ったもので、残りは kodama の事情で決めた。
- **調べたが原文に届かなかったもの。**
  X の @grok の記憶の仕組みは公式の資料が見つからなかった。
  Hermes の Issue #22620（スキル一覧が膨らんで文脈が増える）と OpenClaw の Issue #45608 は、GitHub が 403 を返して読めなかった。
  同じセッションで何十回も圧縮を回し、要約の作り直しと足し込みを比べた独立の測定も見つからなかった。
- **資料どうしで食い違ったもの。**
  OpenClaw のセッションが毎日自動で捨てられるかは、zenn の記事（毎日午前4時に破棄）と公式のドキュメント（既定は自動リセットなし）で食い違う。
  公式のドキュメントを採った。

## 決めてほしいこと

- アーカイブしたエントリをどれだけの期間残す必要があり、誰が消してよいか。
- スキルの変更を誰が、どの RPC で巻き戻してよいか。
- 記憶係にどのモデルを使うか。
- 書き込みを減らす代わりに、UI に流れるストリームの更新をどこまで粗くしてよいか。
