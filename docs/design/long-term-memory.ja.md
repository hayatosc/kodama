# 長く動き続けるエージェントの長期記憶

状態：提案。
この文書の内容はまだ実装していない。
英語版は [long-term-memory.md](long-term-memory.md) にある。

Kodama のエージェントは、常駐するボットのように使うことを想定している。
1つのエージェントが同じ会話で何週間も何か月も、返事と作業を続ける。
この文書は、エージェントが大事なことを覚えたまま、それ以外を手放す仕組みを提案する。
目的は、モデルに渡す文脈も、Durable Object（以下 DO）の保存領域も、際限なく増えないようにすることである。
あわせて、すべてのデータを DO に置く形は採らない。
DO に置くのは Pi Durable のセッション（文脈と会話の記録）だけにし、長期記憶は別の置き場に移す。

## 何が問題か

いまの kodama では、1つのエージェントが SQLite を使う DO 1つに対応し、その DO が Pi Durable のセッションを持っている。

### 文脈はすでに縮められる

Pi Durable には、古い会話を要約して文脈を縮める **compaction** が組み込まれている。
kodama は compaction の設定をしていないので、既定値（`reserveTokens` 16384、`keepRecentTokens` 20000、`backgroundTokens` 32768）で自動に動いている。
モデルが見る量については、すでに上限がある。

### 保存領域は減らない

Pi Durable のエントリ（会話の1件ごとの記録）は不変で、消されない。
仕様書には「head は以後の文脈を変えるだけで、古いエントリをストレージから消さない」とある（Pi Durable spec §2.1）。
compaction も `reset()` も、モデルに見せる範囲の先頭を動かすだけである。
終わったタスクの記録や、システムプロンプトのセクションが変わったときの記録も残り続ける。
Pi には、これらを削る公開の API が無い。

### DO の上限は 10 GB

SQLite を使う DO は、1つあたり 10 GB（無料プランは 1 GB）が上限である。
上限に達すると、書き込みは `SQLITE_FULL` で失敗する。
読み取りと削除はできるが、エージェントとしては動けなくなる。

### 要約にすべては残らない

Pi の要約は、コーディングエージェントと同じ構造化したチェックポイントの形式で作られ、前回の要約を引き継ぐ（spec §8.7）。
既定としてはこれで十分である。
それでも、どんな要約も回数を重ねると細部を落とす。

- **要約ドリフト**：圧縮のたびに、まれな細部が黙って捨てられる（arXiv 2603.07670）。
- **上書きと検索の差**：原文を残して検索で戻せる方式は、どの圧縮頻度でも再現率が 0.95 前後だった。要約で上書きする方式は 0.33〜0.56 で、圧縮の頻度が高いほど悪かった（arXiv 2607.08032、小規模な実験）。

対策は、Pi の要約を自前のものに置き換えることではない。
事実と生の記録を要約の外に持っておくことである。

### 終わらない1セッションは学習にも悪い

Hermes Agent のドキュメントは、Discord などのチャットについてこう書いている。
リセットしないと1つのセッションが何週間も続き、伸び続ける履歴に compaction が繰り返し走って高くつく。
さらに、忘れる、記憶から思い出す、過去のセッションを検索する、という学習のループがほとんど回らない。
Grok Bot のように同じ会話を担当し続ける使い方は、まさにこの状況にあたる。

## Cloudflare の費用はどこで出るか

価格は Cloudflare の料金ページ（Workers Paid、2026年10月時点）から取った。
無料枠はアカウント全体で1か月あたりの量である。

| 項目                        | 価格                                                          | 無料枠     |
| --------------------------- | ------------------------------------------------------------- | ---------- |
| DO の稼働時間               | 100万 GB 秒あたり 12.50 ドル。動いている間、128 MB 分で数える | 40万 GB 秒 |
| DO または D1 の行の書き込み | 100万行あたり 1.00 ドル（削除も数える）                       | 5,000万行  |
| DO または D1 の行の読み取り | 100万行あたり 0.001 ドル                                      | 250億行    |
| DO の SQLite の保存量       | 1 GB 月あたり 0.20 ドル                                       | 5 GB       |
| D1 の保存量                 | 1 GB 月あたり 0.75 ドル                                       | 5 GB       |
| R2 Standard の保存量        | 1 GB 月あたり 0.015 ドル                                      | なし       |
| R2 の書き込みと読み取り     | 100万回あたり 4.50 ドルと 0.36 ドル                           | なし       |

1つのエージェントが1日8時間モデルの出力をストリームし、それを30日続けた場合を見積もる。
無料枠を使い切ったあとの追加分として数えている。

| 費用の出どころ                                                                                                      | 見積もり                   | 減らし方                          |
| ------------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------------------------- |
| ストリーム中の Pi の進捗の書き込み。100 ms（`progress.partialIntervalMs`）ごとに最大1回コミットし、1回で1行以上書く | 860万行以上、8.6 ドル以上  | 間隔を広げる                      |
| モデルの応答を待つあいだの稼働時間                                                                                  | 10万8,000 GB 秒、1.35 ドル | モデルが動く間は避けられない      |
| `subscribe()` のストリームを1日中開けておく（ハイバネーションしない）                                               | 32万4,000 GB 秒、4.05 ドル | 誰も見ていないストリームを閉じる  |
| 会話の記録 1 GB を DO に置いておく                                                                                  | 月 0.20 ドル               | R2 にアーカイブする（0.015 ドル） |

進捗のコミット1回で何行書くかはまだ測っていない。
段階1で、結合テストの中で `SqlStorageCursor.rowsWritten` を使って測る。

ここから2つのことが言える。

1. **大きな費用は書き込みの量と稼働時間であり、保存しているバイト数ではない。**
   データを DO の外に出しても、この2つは減らない。
   減らせるのは、Pi の進捗の間隔とストリームを開けておく時間である。
2. **長期記憶は、エージェントの DO に置くべきではない。**
   1行あたりや 1 GB あたりで比べると、DO は D1 より高くない。
   それでも長期記憶を DO の外に置く理由は3つある。
   - 長期記憶はエージェントの間で共有したい。
   - UI や整理の処理が、エージェントの DO を起こさずに長期記憶を読めるようにしたい。
   - セッション自身の行は、時間とともに消していく。

## 設計を決める9つの知見

調査で分かったことのうち、設計に直接効くものを並べる。

1. **原文は取り出せる形で残す。**
   検索で戻せる圧縮は、要約で上書きするだけの圧縮より強い（2607.08032）。
   OpenClaw も Hermes も Cloudflare も生の履歴を残している。
   よく使う保存領域から消すのはかまわないが、唯一の写しを消してはいけない。
2. **compaction は Pi に任せる。**
   Pi はすでに、切れ目を選び、構造化した形式で要約し、前回の要約を引き継ぎ、失敗したらやり直し、文脈があふれたときにも立て直す。
   自前の要約が効くという根拠は、別の場面のもの（ACE が書き直すのは会話ではなく手引き）か、ベンダー自身の測定（Factory）である。
   要約を自前で持つと、そのプロンプト、失敗、劣化まで kodama が背負うことになるが、得られるものははっきりしない。
   観測マスク（古いツール出力を伏せる。2508.21433）も同じ種類の最適化なので、ツール出力が文脈の大半を占めると測れてから考える。
3. **記憶は compaction からではなく、会話の記録から抽出する。**
   OpenClaw が compaction の直前に記憶を書き出すのは、文脈がエージェントの見る唯一の場所だからである。
   kodama では compaction は保存領域から何も消さないので、エントリは消すまで `scanEntries` で読める。
   抽出は、エージェントがアイドルになったあとに裏で行えばよく（Grok Build や Hermes と同じ）、古い行を消す前には必ず行う。
4. **抽出したものは確かめる。**
   記憶システムの誤りは抽出と更新の段階で生まれて溜まる（HaluMem、2511.03506）。
   抽出した内容は原文と突き合わせて確かめ、出どころを付けて保存する。
5. **事実と出来事では寿命が違う。**
   事実は時間で薄れさせず、新しい事実で置き換える。
   出来事は新しさで順位を下げる（2604.11364、Zep の辺の無効化、Generative Agents の減衰係数 0.995）。
   モデルは古くなった事実をそのまま受け入れがちなので（STALE、2605.06527 で正答率 55.2%）、置き換えは明示的に記録する。
6. **スキルは、検証できた経験から作る。**
   成功して検証できた軌跡から作ったスキルは効いた（AWM で相対 24.6% と 51.1%、ASI で 23.5%、ReasoningBank）。
   作業の前にエージェント自身が書いたスキルは、スキル無しより 8.1〜11.5 ポイント悪かった（SkillsBench）。
   小さく絞ったスキルのほうが大きな束より良く、更新を重ねると散らかる（SkillEvolBench）。
   一覧から選ぶ精度は、64個を超えたあたりから落ちる（2607.10113）。
   使われないスキルは片付ける必要がある（Hermes の curator は14日で stale、30日でアーカイブし、自動では消さない）。
7. **共有の記憶は、攻撃と不整合の入口になる。**
   ふつうの利用者でもエージェントの記憶に細工できる（MINJA）。
   悪意ある「成功体験」を植え付けると、長く残る（MemoryGraft）。
   既存のプロンプトインジェクション対策では、記憶の汚染を防げない（MPBench）。
   共有ブロックを複数のエージェントが同時に丸ごと書き直すと、更新が失われる（Letta）。
   共有の書き込みには、出どころ、記録ごとに1人の書き手、レビューが要る。
8. **常に読み込む記憶は、区切りでだけ変える。**
   Hermes は、プロンプトのキャッシュを効かせるために記憶をセッション開始時に固定している。
   Pi も、セクションが変わるとそれを新しいシステムエントリとして送り直す。
   常に読み込む記憶は、アイドルの区切りでだけ更新する。
9. **記憶には専用の書き手を置く。**
   Letta は、記憶の編集を会話するエージェントから外し、別の sleep-time エージェントに移した。
   記憶の管理と会話を1つのエージェントにまとめると、遅くなり、信頼性も落ちたからである。
   会話するエージェントに残したのは検索のツールだけである。
   Cloudflare Agent Memory も「主のエージェントは、保存の戦略に文脈を使うべきではない」と書いている。
   Hermes は記憶の見直しを安いモデルで走らせることができる（3〜5倍ほど安くなる）。
   書き手が1人なら、知見7の不整合の問題も片づく。

## 設計

### 保存の層

| 層         | 置き場                            | 中身                                                                                         | 寿命                                 |
| ---------- | --------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------ |
| セッション | エージェントの DO（いまのまま）   | Pi Durable のセッション、常に読み込む記憶の写し                                              | 古い行を消していく                   |
| 長期記憶   | D1 のデータベース `MEMORY_DB` 1つ | 記憶の記録と FTS5 の索引、抽出のチェックポイント、共有の記憶への提案、スキルの索引、変更記録 | 残す                                 |
| アーカイブ | R2 のバケット `ARCHIVE`           | 消したエントリの塊と、塊ごとのマニフェスト（範囲、要約、件数、SHA-256）、スキルの本体        | 保持期間の規則で決める               |
| 任意       | Vectorize                         | 記憶の記録の埋め込み                                                                         | 検索の取りこぼしが見えたときだけ足す |

新しい DO のクラスは `MemoryAgent` だけである。
これは `Agent` を継承したクラスで、Worker の内部からしか呼べない（後述）。
エージェントは Worker のバインディングを通して D1 と R2 を読む。
長期記憶を書くのは記憶係だけである。

長期記憶を D1 に置くのは、次の理由による。

- FTS5 による全文検索が使える。
- 30日分のどの時点にも巻き戻せる（Time Travel）。
- UI の Worker や整理の処理が、エージェントの DO を起こさずに読める。

D1 のデータベースは1つ 10 GB までだが、記憶の記録は小さい。
もし足りなくなっても、D1 は小さなデータベースを多数に分けて使う前提で作られているので、エージェントのまとまりごとなどに分けられる。

### 記憶の範囲

| 範囲                                                   | 中身                                                                         | 誰が書くか                         |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------- |
| **文脈**                                               | いまのターン、compaction の要約                                              | セッションの DO の中の Pi          |
| **エージェント**（`agent:<id>`）                       | そのエージェントのメモ、身につけた約束ごと、出来事、そのエージェントのスキル | 記憶係                             |
| **共有**（`shared:<space>`、たとえば `shared:global`） | チームの約束ごと、共有の事実、共有のスキル                                   | 記憶係（レビューを通ったものだけ） |

人ごとの記憶は持たない。
一緒に働く人についての事実が仕事に関わるなら、それはふつうのエージェントの事実として残す。

### 部品と呼び出しの関係

記憶係は `MemoryAgent` である。
`Agent` を継承したクラスで、Pi のセッション、受付の列、復旧のアラームはそのまま同じものを使う。
別の DO のクラスとして公開し、インスタンスは1つだけにする。
そのバインディングを持つのは、内部の呼び出し元だけである。

```text
AgentService（公開の RPC の入口）
  `-- AGENTS ---------------------> Agent DO（agentId）  ここから MemoryAgent には届かない

Agent DO（agentId）
  |-- 読む -----------------------> D1 MEMORY_DB         memory_search、スキル、常に読み込む記憶
  |-- MEMORY_AGENT.sendMessage ---> MemoryAgent DO       remember、アイドル時の抽出、古い行を消す前
  `-- 書く -----------------------> R2 ARCHIVE           消す前のエントリ

MemoryAgent DO（ただ1つのインスタンス "memory"）
  |-- 読み書きする ---------------> D1 MEMORY_DB         記憶を書くツールを通して
  |-- 読む -----------------------> R2 ARCHIVE           統合の根拠、スキルの本体
  |-- AGENTS readEntries ---------> Agent DO             抽出のときだけ。ページ単位で読む
  `-- AGENTS memoryChanged -------> Agent DO             次のアイドルで常に読み込む記憶を読み直させる

scheduled ハンドラ -------------> MemoryAgent DO       1日1回の統合
```

新しく足すバインディングは、`MEMORY_AGENT`（DO）、`MEMORY_DB`（D1）、`ARCHIVE`（R2）の3つである。
`AgentService` は `AGENTS` しか解決しないので、UI もほかの RPC の呼び出し元も、記憶係に送ることも、購読することも、設定することもできない。
利用者が `memory` という名前のエージェントを作っても、記憶係とは関係がない。

### D1 のテーブル

スキーマの案は [long-term-memory.sql](long-term-memory.sql) に置いた。
これを D1 のマイグレーションとして、`cf d1 migrations` で管理する。

| テーブル                 | 1行が表すもの                                                                   | 書くもの                 |
| ------------------------ | ------------------------------------------------------------------------------- | ------------------------ |
| `memory_records`         | 記憶1件（事実、出来事、指示、タスク）。範囲、状態、出どころ、元のエントリを持つ | 記憶係                   |
| `memory_fts`             | `memory_records` に対する FTS5 の索引（外部コンテンツ方式。トリガーで同期する） | トリガー                 |
| `extraction_checkpoints` | エージェントごとの、抽出を終えた最後のエントリ                                  | 記憶係                   |
| `skills` と `skills_fts` | スキルの索引（名前、説明、状態、R2 のキー、根拠）と、その検索用の索引           | 記憶係                   |
| `shared_proposals`       | 共有の記憶への提案（保留、受け入れ、却下）                                      | 記憶係。判断はレビュー役 |
| `memory_ledger`          | すべての変更を追記だけで残す記録。断った候補も残す                              | 記憶係、レビュー役       |

セッションや世代のテーブルは作らない。
Pi はエントリの ID を使い回さず、古い行を消してもセッションは同じまま続くので、エージェントのエントリは一生を通じて1本の列になる。
アーカイブは、エントリの範囲で識別する。

テーブルの形を決めた規則は次のとおり。

- **記録の id**：範囲、種類、話題キー、内容、元（エージェントと最初のエントリ）から作る SHA-256。同じ仕事を繰り返しても新しくは書かれない（`INSERT OR IGNORE`）。ユーザーが同じ事実をあとでもう一度言ったときは、新しい記録になり、置き換え済みの記録とはぶつからない。
- **1つの話題に有効な記録は1つ**：`status = 'active'` の行だけを対象にした `(scope, kind, topic_key)` の部分一意インデックスを張る。これでロック無しに安全に置き換えられる。記憶係は、古い記録を置き換え済みにする文と新しい記録を足す文を、1つの `batch()`（D1 のトランザクション）で送る。ほかの書き込みが先に置き換えていたら、足す文がインデックスに反してバッチ全体が取り消されるので、記憶係は読み直してやり直す。
- **`superseded_by` は外部キーにしない**：D1 は外部キーをその場で検査するが、古い行に印を付けるのは新しい行ができる前だからである。
- **`origin`**：その記録がある理由を残す。値は `user_request`、`agent_judgment`、`extraction`、`consolidation`、`archive`（アーカイブしたエントリの範囲の要約）のどれか（`trigger` という名前は SQL の予約語とぶつかるので使わない）。
- **時間の上での有効さ**：`observed_at`（それが本当になった時点）と、置き換えや無効化を記録した変更記録から分かる。有効期間のための別のテーブルは作らない。
- **チェックポイントの書き手は1人**：記憶係であり、受付の列を1件ずつ処理する。もし2つの仕事が同じ範囲を扱っても、内容から作る id のおかげで害は無い。

主な問い合わせは次のとおり。

- **常に読み込む記憶**：エージェントの範囲と共有の範囲にある有効な `instruction` と `fact` を、`pinned`、`importance`、`last_used_at` の順に並べ、文字数の予算に収まるところまでをコードで切り出す。ブロック用の別のテーブルは作らない。統合は、重要度と固定（pin）を調整することで結果の形を整える。
- **`memory_search`**：`memory_fts MATCH ?` を、許された範囲の有効な記録とつなぎ、`bm25()` で並べてから、コードで新しさと重要度を加味する。返した行の `use_count` と `last_used_at` は1つの文でまとめて更新する。結果1件につき1行の書き込みがかかる。

#### Intl.Segmenter による日本語の検索

FTS5 の標準のトークナイザ `unicode61` は空白と句読点でしか区切らないので、日本語の文はまるごと1語になってしまう。
そこで `trigram` のトークナイザは使わず、Worker の中で `Intl.Segmenter` を使って文を単語に分け、空白で区切って `search_text` 列に入れる。
FTS5 はその単語を `unicode61` で索引にする。
この方式なら、`trigram` では引けない「使う」のような2文字の語も引ける（`trigram` は3文字以上が要る）。
索引も小さく済むはずである（trigram は文字の位置ごとに索引を作る）。
`bm25()` による順位付けも単語単位になる。
D1 に確実にある標準のトークナイザしか使わないので、本番の D1 が何に対応しているかを気にしなくてよい。

これは [個人開発に無料の日本語全文検索を](https://zenn.dev/coji/articles/cloudflare-d1-fts5-japanese-search-api)（Coji Mizoguchi、2026）と同じ方式であり、試した結果をもとに、カタカナの扱いと前方一致でのやり直しを足した。

`search_text` の作り方は次のとおり。

1. NFKC で正規化し、小文字にする（全角の「ＰＮＰＭ」は `pnpm` になる）。
2. `new Intl.Segmenter('ja', { granularity: 'word' })` で分け、`isWordLike` の断片だけを残す。
3. 記事の提案にならい、各断片の中でカタカナの後の長音記号を取り除く。これで「サーバ」と「サーバー」が一致する。分けたあとで行うのは、分ける前に行うと辞書の切り方が変わってしまうからである。代わりに、「ラーメン」と「ラメン」のような組は区別できなくなる。
4. 続いたカタカナの断片を1語にまとめる。辞書に無い外来語は細かく分かれてしまい（「リポジトリ」は「リ / ポジ / トリ」になる）、そのままでは前方一致の検索が当たらない。
5. まとめた語と異なる元の断片を後ろに足す。こうすると複合語の一部でも当たる（「マネージャー」で「パッケージマネージャー」が見つかる）。

問い合わせの作り方は次のとおり。

1. 問い合わせにも同じ手順をかけ、まとめた語をそれぞれ引用符で囲んで並べる。FTS5 はこれを `AND` として読む（`"pnpm" "を" "使う"`）。ここは記事と同じである。
2. 何も返らなければ、各語を前方一致にしてやり直す（`"デプ"*` で「デプロイ」が見つかる）。

当たらないと分かっているのは、長いカタカナの複合語の中にある語のうち、文脈によって辞書の切り方が変わるものである。
「プラクティス」は単独なら1語だが、「ベストプラクティス」は1文字ずつに分けられるので、「プラクティス」では見つからない。
単語に分ける方式ではこれは直せない。
trigram なら直せるが、上で挙げた問題を抱えることになる。

`search_version` には、その行をどの切り方で作ったかを残す。
切り方の規則や、実行環境の ICU のデータが変わったら、統合が古い版の行を切り直す。
索引は FTS5 のトリガーが更新する。

保持期間を過ぎたものは、統合が少しずつ消す（アーカイブした出来事と古い変更記録）。
D1 は大きな削除を分けて行うよう求めている。
データベース全体の巻き戻しは、Time Travel で30日分できる。

このスキーマは SQLite 3.45 で確かめた。
部分インデックスは同じ話題の2つ目の有効な記録を弾き、古い前提で置き換えようとしたバッチは取り消された。
`Intl.Segmenter` は workerd（2026-10-12）でも動かし、Node と同じ切り方になることを確かめた。
上の規則で、「使う」「リポジトリ」「リポ」「デプ」「マネージャー」「レビュー」「サーバレス」と「サーバーレス」「ベストプラクティス」「ＰＮＰＭ 使う」「pnpmを使う」は目当ての記録に当たった。
「プラクティス」は、上で書いたとおり当たらなかった。

### 種類ごとの寿命

- **fact（事実）**：薄れさせない。同じ話題キーの新しい事実が来たら置き換え、置き換えの鎖を残す。
- **event（出来事）**：新しさで順位を下げる（半減期は設定でき、既定は OpenClaw と同じ30日）。保持期間を過ぎたらアーカイブする。
- **instruction（指示）**：複数の手順からなるものは、統合処理でスキルの候補にする。
- **task（タスク）**：終わったら捨てる。

本当に消す（プライバシーのための削除）のは運用者の操作であり、エージェントにはさせない。

### 常に読み込む記憶

Pi のプロンプトセクションとして、上限付きのブロックを出す。
中身は、D1 の記録から作る2つのブロック（エージェント自身の記憶と、小さな共有ブロック）である（前述の主な問い合わせを参照）。
各ブロックには文字数の予算があり、使用量をプロンプトに表示する（Hermes は `[67% — 1,474/2,200 chars]` のように出している）。
セッションの DO は、起動したときと、アイドルのあいだに記憶係から仕事の完了を知らされたときに D1 からブロックを読み、表示する内容を Pi のドキュメントに写しておく。
そのあいだのリクエストはこの写しを使うので、プロンプトの先頭が変わらず、リクエストごとに D1 を待つこともない。

### 記憶係

長期記憶の書き手は1人にする。
これを**記憶係**と呼ぶ。
仕事をするエージェントは、記憶を読むことと、覚えてほしいことを頼むことだけをする。

- **何か**：`MemoryAgent extends Agent` で、インスタンスは `memory` という名前の1つだけ。`Agent` の実装をまるごと使い、記憶係にするところだけを上書きする。上書きするのは、コードで決めた固定の設定（`MEMORY_MODEL_PROVIDER` と `MEMORY_MODEL_ID` で選ぶ安いモデルと、記憶係用のシステムプロンプト）、ツールの登録表、仕事ごとのリセット、自分の会話の記録に裏での抽出をかけないこと、である。`setConfig` は使えない。
- **内部専用**：バインディングは `AgentService` に含めないので、仕事は kodama 自身のコード（仕事をするエージェントのツール、古い行の削除、`scheduled` ハンドラ）からしか届かない。利用者と話すことはなく、誰かが眺める会話も持たない。
- **記憶係だけが持つツール**：`memory_write`、`memory_supersede`、`memory_decline`、`read_entries`、`skill_propose`、`shared_propose`、`notify_memory_changed` は、`MemoryAgent` の登録表にだけ載せる。仕事をするエージェントの登録表にはそもそも無いので、どんな設定をしてもほかのエージェントでは使えない。
- **決まった形の仕事**：仕事は valibot で検証する JSON のメッセージ（`remember`、`extract`、`record_archive`、`consolidate`）であり、自由な会話ではない。
- **仕事の届け方**：どのエージェントも持っている `sendMessage` を、`MEMORY_AGENT` バインディングに対して呼ぶ。受け付けは永続化され、モデルの応答を待たないので、送る側は止まらない。記憶係が忙しいあいだに届いた仕事は Pi が列に積み、1件ずつ順に処理する。これでロック無しに書き手が1人になる。
- **重複の排除**：仕事の `requestId` は、元のエージェント、元のエントリ、内容から作るハッシュにする。同じ ID で届けなおしても、すでにある受付が返り、仕事は2回走らない。
- **記憶係自身の文脈**：仕事どうしは独立している。記憶係は仕事が1件終わるたびに文脈をリセットする（受付が片づいたときに Pi の `reset()` を呼ぶ、エージェントごとの設定）。各仕事は小さな文脈から始まり、保存領域はほかのエージェントと同じく、古い行を消して空ける（抽出の手順は飛ばす）。記憶係自身には裏での抽出をかけないので、自分の会話の記録を材料にすることはない。
- **費用**：モデルを待つあいだ、DO の稼働時間が課金される。仮に1日1,000件、1件10秒とすると、月に約3万7,500 GB 秒で、無料枠を超えた分は 0.47 ドルほどである。`Agent` を使い回すことの価値に比べれば小さい。
- **置き換えの安全**：どの書き込みも、記録の置き換えは部分一意インデックス（D1 のテーブルを参照）を通して行う。運用者が手で書いても、1つの話題に有効な記録が2つになることはない。
- **仕事をするエージェントのツールは少なくする**：`memory_search`、`history_search`、`skill_search`、`skill_load`、`remember` だけを持つ。`remember` は記憶係にその場で仕事を送る。記憶の記録そのものは書かない。

### 書き込みの経路

ここに挙げる書き込みは、どれも記憶係が行う。

**1. ターンの中で覚える。**
仕事をするエージェントは、次の2つの場合にそのターンの中で `remember` を呼ぶ。

- **ユーザーが頼んだとき**：「〇〇を覚えて」と言われたときや、「いつも〇〇して」「これからは〇〇して」のような続けて守る指示を出されたとき。OpenClaw も「覚えてほしいことは、エージェントにそう頼めばよい」としている。
- **エージェントが自分で残すべきと判断したとき**：誰も「覚えて」と言っていなくても、あとのセッションで要るとエージェントが気づいたとき。たとえば、決めたことと理由、ユーザーからの訂正、失敗から学んだこと、調べてようやく分かった長く変わらない事実である。Hermes や Claude の memory tool も、エージェントにこのやり方で記憶を管理させている。

何を残し、何を残さないかはプロンプトで示す。
Grok Build にならい、約束ごと、理由つきの決定、長く変わらない事実は残し、作業の途中の状態、まだ固まっていない結論、秘密情報、リポジトリやドキュメントにすでに書いてあることは残さない。
一度きりの作業の依頼は覚えない。
1ターンで受け付ける `remember` の数には上限を設ける。

どちらの場合も、同じ道筋をたどる。

1. ツールは、依頼を valibot で検証し、大きさに上限を設け、インジェクションの型を検査する。
2. 依頼、その出どころ、それが出てきたエントリの ID を載せて、`sendMessage` で記憶係にその場で `remember` の仕事を送る。リクエスト ID はエージェント ID、元のエントリ、内容から作るハッシュなので、再起動のあとにツールの呼び出しが繰り返されても、すでにある受付が見つかり、2つ目の仕事は始まらない。
3. ツールは、仕事が永続的に受け付けられた時点で戻る。ターンは止まらず、記憶係がモデルを待つ時間が仕事をするエージェントの稼働時間として課金されることもない。
4. 記憶係は依頼を分類し（たいていは指示か事実）、既存の記録と照らし（新しい指示が、それに取って代わられる古い指示を置き換える）、D1 に書く。会話の記録を読み直すのではなく、小さなモデル呼び出しを1回するだけである。
5. 書き終えたら、記憶係は仕事をするエージェントの DO に記憶が変わったことを知らせる。常に読み込む記憶には次のアイドルの区切りで反映される。それまでも、指示はいまの文脈に残っている。同じ範囲を読むほかのエージェントには、それぞれの次の読み直しで反映される。

あとで抽出が同じメッセージを会話の記録の中に見つけても、同じ内容の記録がすでにあるので、新しくは書かない。

記録の出どころには、どちらの場合かを残す（`user_request` か `agent_judgment`）。
ユーザーの依頼は、頼まれたとおりに書く。
ただし、ユーザーが前に頼んだ記録とぶつかるときは、新しいほうで置き換える。
エージェントの判断によるものは候補として扱う。
記憶係は重複や価値の低いものを断ることがあり、重要度は低めから始め、使われないままなら統合のときにアーカイブする。
エージェントが気づいたことを何でも残すと、選んで足すことで避けられる「誤りの伝播」を繰り返すことになる（2505.16067）。

その場で誰も気づかなかったことは、裏での抽出（後述）が拾う。

**2. 抽出。**
エージェントがしばらくアイドルになったとき（そのエージェントの DO のアラーム）と、古い行を消す前に必ず、仕事をするエージェントが記憶係に抽出の仕事を送る。
Pi の compaction には手を出さない。

1. 記憶係は、抽出の区切り（チェックポイント）より後のエントリを `read_entries` ツールで読む。このツールは、仕事をするエージェントの DO のページ単位の RPC を呼ぶ（中では `scanEntries` を使う）。
2. 安いモデル（設定で選ぶ）で、記録の候補を抽出する。
3. 各候補を、根拠として挙げたエントリと突き合わせ、裏付けの無いものは捨てる。
4. D1 の既存の記録と照らし、追加する、置き換える、無効にする、何もしない、のどれかを選ぶ（Mem0 の ADD、UPDATE、DELETE、NOOP に近いが、削除せず置き換える）。
5. 書き込みと同じバッチで、D1 のチェックポイントを進める。

記録の id を内容から作り、`INSERT OR IGNORE` で書くので、途中で止まった仕事が再開しても重複して書かない。

**3. 統合。**
多くて1日1回程度、Cron トリガーが記憶係に仕事を送る。
エージェントを1つずつ起こさず、記憶係が D1 に対してまとめて行う（sleep-time compute や、OpenClaw と Devin の dreaming と同じ発想）。
重複をまとめ、矛盾を解消し、出来事の順位を下げ、常に読み込むブロックを予算内に作り直し、スキルを作り、共有の記憶への提案を用意する。
作り直しは差分の編集で行い、丸ごと書き直さない。
根拠が要るときは、R2 にアーカイブした会話の記録を読む。
抽出はプロンプトで決めた手順に沿って進めるが、統合ではツールをより自由に使わせる。
根拠を探しに行き、何をまとめるかを判断する必要があるからである。

### 読み出しの経路

- 常に読み込むブロック（前述）。
- `memory_search`：D1 の FTS5 の BM25 に、新しさと重要度を掛けて並べる。結果には出どころも付ける。
- `history_search`：D1 にある `archive` の出来事の記録（アーカイブした範囲ごとに1件の要約）を探し、当たった範囲を R2 から読む。R2 のキーはエージェント ID とエントリの範囲から決まる。抽出で取りこぼした細部を拾う安全網になる。

### compaction

compaction は Pi の仕事である。
kodama は Pi の既定値をそのまま使い、計測の結果が必要を示したときだけ `src/harness.ts` で方針を変える。
あとでツール出力が文脈の大半を占めると分かったら、要約に手を入れる前に、`beforeRequest` フックでの観測マスクを試す。

### セッションの保存領域を空ける：アーカイブして消す

保存領域が埋まってきたら、エージェントはいちばん古いエントリを R2 にアーカイブして消す。
会話も、いまの文脈も、DO もそのまま残る。

**消してよいもの。**
Pi がモデルに渡す文脈を作るのは、いちばん新しい境目（head）から後だけである。
compaction や reset のあとは、その時点で有効なセクションとツールをすべて含んだシステムのエントリが新しく書かれる（spec §2.1 の規則10）。
境目より前のエントリを読むのは履歴の一覧 `entries()` だけで、kodama はこれを使っていない。
そこで、消してよいのは次のものとする。

- ルートの会話のエントリのうち、ID がいちばん新しい境目（`P`）より小さいもの。
- 終わったタスクの記録と、そのタスクに属するドキュメントとその版。
- リクエスト ID を覚えておく期間（既定は30日）より古い、片づいた受付の記録。
- 以上の `record_ids` の行。

`pi.live` のような Pi 自身のドキュメントは、Pi がもともと最新の版だけを残しているので、消す必要は無い。

**いつ消すか。**
エージェントがアイドル（動いているタスクが無い）で、ルートの会話が唯一の会話であり（kodama はいまほかの会話を作らない。もし作るようになったら消す処理は飛ばす）、`ctx.storage.sql.databaseSize` が閾値（たとえば 1 GB）を超えたか、消してよいエントリの数が一定を超えたときに行う。
DO が 10 GB の上限に達しても削除はできる（Durable Objects の FAQ）ので、すでに満杯になった DO もこの処理で戻せる。

**手順**は、そのエージェント自身の DO が進める。

1. 抽出のチェックポイントが `P - 1` より手前なら、`P - 1` までを対象に `extract` の仕事を送り、片づくまで待つ。
2. 前回消したところの次から `P - 1` までのエントリを、R2 の `archive/<agentId>/<first>-<last>.jsonl` に書き出し、その塊のマニフェスト（範囲、件数、SHA-256、境目の要約）を書いて確かめる。もう一度書き出しても同じキーに書くだけなので、やり直しても害は無い。
3. `record_archive` の仕事を送り、記憶係に要約を `archive` の出来事の記録として `history_search` 用に残させる。
4. `blockConcurrencyWhile` の中で、harness を閉じ、消してよい行を1つの `transactionSync` で消し、`P` を消した境目として kodama の小さな表に記録し、harness を開き直し、復旧のアラームを張り直す。

トランザクションは全部か無しかで、書き出しが先なので、途中で落ちても「何も消えていない」か「確かめたアーカイブがそろっている」かのどちらかになる。
モデルに渡す文脈と `snapshot()` は、消す前と後で同じである。
開いている `subscribe()` のストリームは harness を閉じたときに終わり、つなぎ直すと同じ状態が見える。

**確かめたこと。**
workerd の結合テスト（一度だけ流し、コミットはしていない）で、3往復の会話のあと compaction し、エントリ8件中6件と、終わったタスク4件をすべて消した。
DO を追い出したあとも、エージェントは新しいメッセージに答えた。
モデルへのリクエストには要約が入り、消した本文は入っていなかった。
`snapshot()` には、要約、残った返答、新しいやり取りが並んだ。
消したターンのリクエスト ID で送り直すと、モデルを呼ばずに元の受付が返った。
ローカルの workerd では、20 MB の表の75%を消すと `databaseSize` が 20.5 MB から 5.1 MB に減った。
本番では測っていない。
古い受付の記録を消す部分は、まだ試していない。

**危うさ。**
この処理は Pi の内部のテーブルに書き込む。
内部のテーブルは公開の API ではない。
kodama は Pi の版を固定し、この処理を1つのモジュールにまとめ、Pi を上げるたびに専用のテスト（会話を続ける、もう一度 compaction する、追い出す、アラームから復旧する、取り消す、リクエスト ID の重複を排除する、snapshot を比べる）を流す。
Pi Durable に公式の保持期間の API ができれば、このモジュールはそれに置き換える。
kodama からも上流に提案するべきである。
この処理を入れるまでは、エージェントはいまと同じように上限へ向かって増えていくだけである。

### スキル（手続きの記憶）

- **形式**：Agent Skills（`name` と `description` を前書きに持つ `SKILL.md`）。Hermes、OpenClaw、Claude Code と互換にする。
- **置き場所**：索引（名前、説明、範囲、状態、使用回数、R2 のキー）は D1 に、本体と付属のファイルは R2 に置く。
- **見せ方**：プロンプトのセクションには、名前と説明を多くても数十個だけ並べる。残りは `skill_search` で探し、`skill_load` で R2 から本体を読む。
- **作り方**：記憶係が統合の中で、少なくとも2回成功した手順だけを候補にする。候補には根拠の軌跡と、失敗から学んだ注意点を付ける。再実行かチェックに通ったら有効にし、共有のスキルはさらにレビューを通す。仕事をするエージェントはスキルを書かず、作業の前にスキルを書くこともしない。
- **片付け**：14日使われなければ stale、30日でアーカイブする。固定（pin）したものは対象外にする。アーカイブは元に戻せ、すべての変更を書き手と一緒に記録する。

### 共有の記憶と安全

- 共有の記録は直接書かない。複数のエージェントが頼っているエージェント範囲の記録から、記憶係が出どころ付きの提案を作り、レビュー役が受け入れるか退ける。レビューの UI ができるまでは、運用者の RPC で行う。
- 共有の記録は、記録ごとに書き手を1人に決める。更新はブロックを書き直さず、新しい版を作る。
- 信頼できない出どころから来た内容は、出どころ付きの証拠として残すだけにし、レビューなしで常に読み込む記憶には上げない（OpenClaw も信頼できない報告を同じように扱う）。
- 秘密情報は保存しない。書く前に伏せる（Codex と Grok Build も秘密情報を記憶から外している）。

### 費用を抑える手段

- 1回のコミットで何行書くかを測ったうえで、`progress.partialIntervalMs` を広げる（たとえば 500〜1000 ms）。代わりに、UI に流れるストリームの更新が粗くなる。
- 誰も見ていない `subscribe()` のストリームは閉じる。あるいは、観測を WebSocket のハイバネーションに移す。
- セッションの DO が大きくなる前に古い行を消す。アーカイブした分は、R2 に置くと保存の単価がおよそ13分の1になる。
- 記憶係には安いモデルを使う。仕事をするエージェントと同じモデルは要らない。
- 統合は、エージェントを1つずつ起こさず、記憶係が D1 に対して1つの仕事として行う。

## 進め方

どの段階でも、モデルをモックした workerd の結合テストを一緒に入れる。

1. **計測と費用の削減。**
   進捗の間隔を明示し、1ターンあたりの書き込み行数、DB の大きさ、文脈の大きさを測る。
   テスト：1ターンあたりの行数が記録した予算を超えないこと。
2. **D1 の長期記憶と記憶係。**
   D1 のマイグレーションとしてのスキーマ、版の番号を持つ共通の単語分け関数、固定の設定とツールを持つ `MemoryAgent`、抽出とチェックポイント、その場で記憶係に仕事を送る `remember`、読み出しのツール、常に読み込むセクションを入れる。
   テスト：ユーザーの依頼でもエージェント自身の判断でも、`remember` を呼ぶと同じターンの中で記憶係に仕事が届き、エージェントがアイドルになる前に記録が D1 にあること。ツールの呼び出しを繰り返しても2つ目の受付ができないこと。エージェントの判断による重複が断られること。仕事をするエージェントが記憶を書くツールを持たず、`AgentService` から記憶係に届かないこと。何度か compaction を経る前に話した事実が、あとで D1 に見つかること。新しい事実が古い事実を置き換えること。途中で止まった抽出をやり直しても重複して書かないこと。抽出が失敗してもチェックポイントは進まず、会話には影響しないこと。
3. **アーカイブして消す。**
   マニフェスト付きの R2 への書き出し、消す処理のモジュール、`archive` の記録と `history_search` を入れる。
   テスト：消したあとも、会話が続き、もう一度 compaction でき、追い出しとアラームからの復旧ができ、取り消しもできること。`snapshot()` が変わらないこと。覚えておく期間の中のリクエスト ID は重複が排除されること。書き出しを確かめるまで行を消さないこと。`databaseSize` が減ること。このテストは Pi を上げるたびに流す。
4. **スキル。**
   D1 の索引、R2 の本体、見せ方、統合処理からの提案、片付け。
5. **共有の記憶。**
   共有の範囲、記憶係からの提案、レビュー。
6. **評価。**
   compaction と古い行の削除のあとに、確認の質問をする（事実の想起、触ったもの、続きから再開できるか、決定の理由。Factory の評価と同じ観点）。
   LongMemEval と同じ観点で、知識の更新、時間に関する質問、答えないべきときに答えないか、も確かめる。

## 検討して採らなかった案

- **すべてを DO に置く**（エージェントごとと共有の範囲ごとに記憶用の DO を作る）。
  動きはするが、共有の記憶には起きたままの DO が別に要り、UI や整理の処理が読むたびにその DO を起こすことになる。
- **古い行を消さない。**
  いちばん簡単で、テキストの会話だけなら 10 GB はかなり遠い。
  しかし上限に当たると止まる。
  段階1と2はこの形のままでも動くので、消す処理は計測の結果を見てから入れてもよい。
- **DO を丸ごと消し、引き継ぎメモから始め直す**（同じ DO での世代交代。この計画の前の版）。
  Pi の公開の API（`reset()` と `deleteAll()`）だけで済むが、会話の続きが途切れ、マニフェストから戻す処理と世代の番号が要り、購読している人もみな切れる。
  Pi の変更で古い行を消す処理が危うくなったときの、代わりの手段として残す。
- **記憶を R2 の markdown ファイルだけで持つ**（OpenClaw や Hermes がディスクに置くのと同じ形）。
  保存はいちばん安く、人が手で直しやすい。
  しかし検索には別の索引が要り、R2 にはトランザクションが無い。
  D1 の記憶を人が読むための markdown として書き出す機能は、あとから足せる。
- **仕事をするエージェントが自分で記憶を書く**（この計画の前の版）。
  すべてのリクエストに記憶のツールと指示が載り、仕事用のモデルを記録の管理に使い、1つの範囲に書き手が何人もいることになる。
  Letta も同じ理由でこの形をやめている。
- **記憶係を、公開の名前空間にある、予約した ID の `Agent` にする**。
  動きはするが、公開の RPC のすべてのメソッドでその ID を弾く必要があり、ツールの制限も設定の検査に頼ることになる。
  継承したクラスに別のバインディングを持たせれば、どちらも構造として外から届かなくなる。
- **記憶係を Cloudflare Workflow にする**（この計画の前の版）。
  Workflows はモデルを待つあいだ課金されないが、`Agent` と Pi Durable がすでに持っているもの（永続的な受け付け、リクエスト ID による重複の排除、順に処理する受付の列、復旧）を、別の実行の仕組み、別のツール、別のテストで作り直すことになる。
  節約できる稼働時間も小さい（前述の費用の見積もりを参照）。
- **compaction の要約を自前で持つ**（Pi の `beforeCompact` フックで記憶を抽出し、足し込み式の要約を返す）。
  記憶が Pi の compaction の処理に縛られ、Pi の要約が問題だという根拠も無いまま、要約の質を kodama が背負うことになる。
  評価の確認質問で、記憶と `history_search` では補えない取りこぼしが見えたときのために、フックは選択肢として残しておく。
- **Pi Durable に公式の削除の API ができるのを待つ。**
  本来はこれがいちばん良い。
  Pi は自分の前提（エントリは不変で ID は使い回さない、fork は親を読む）を知っている。
  上流に提案する価値はあるが、それを待つほどではない。
  kodama の消す処理は、そうした API に差し替えられる形にしておく。
- **Cloudflare Agent Memory を使う。**
  この設計とよく似ていて、`cf` にはすでに `agentMemory` のバインディングがある。
  ただし非公開ベータなので、記憶の保存先はインタフェースの裏に隠しておき、あとで差し替えられるようにする。

## 決めてほしいこと

- 共有の記憶の提案をレビューするのは誰か（UI を通した人か、規則を厳しくした記憶係か）。
- アーカイブしたエントリをどれだけの期間残す必要があり、誰が消してよいか。
- 記憶係にどのモデルを使い、どれだけの費用をかけるか。
- 書き込みを減らす代わりに、UI に流れるストリームの更新をどこまで粗くしてよいか。
