# 長期記憶の設計の理由

状態：提案。
設計そのものは [long-term-memory.ja.md](long-term-memory.ja.md) にある。
この文書は、既存のシステムと論文から何を借り、何を退けて今の構成にしたかを、判断ごとに残す。
英語版は [long-term-memory-rationale.md](long-term-memory-rationale.md) にある。

各判断の「理由」には、外の根拠（既存のシステムか論文）があるものと、kodama の事情だけで決めたものがある。
後者には「kodama の事情」と書く。

## 前提

- **Pi Durable はエントリを消さない。**
  仕様書には「head は以後の文脈を変えるだけで、古いエントリをストレージから消さない」とある（Pi Durable spec §2.1）。
  compaction も `reset()` も、モデルに見せる範囲の先頭を動かすだけである。
  終わったタスクの記録や、セクションが変わったときの記録も残り続け、Pi にはこれらを削る公開の API が無い。
- **文脈はすでに縮められる。**
  Pi Durable の compaction は既定で動く（`reserveTokens` 16384、`keepRecentTokens` 20000、`backgroundTokens` 32768）。
  要約は構造化したチェックポイントの形式で作られ、前回の要約を引き継ぐ（spec §8.7）。
- **DO の上限は 10 GB である。**
  上限に達すると、書き込みは `SQLITE_FULL` で失敗し、読み取りと削除だけが通る（Durable Objects FAQ）。
  エージェントとしては動けなくなる。
- **要約にすべては残らない。**
  圧縮のたびに、まれな細部が黙って捨てられる（要約ドリフト、2603.07670）。
  原文を残して検索で戻せる方式は、どの圧縮頻度でも再現率が 0.95 前後だった。
  要約で上書きする方式は 0.33〜0.56 で、圧縮の頻度が高いほど悪かった（2607.08032、小規模な実験）。
- **終わらない1セッションは学習にも悪い。**
  Hermes Agent のドキュメントは、リセットしないと1つのセッションが何週間も続き、compaction が伸び続ける履歴に繰り返し走って高くつき、学習のループがほとんど回らないと書いている。
  同じ会話を担当し続ける kodama の使い方は、まさにこの状況にあたる。

## 判断

### 1. 長期記憶はエージェントの DO の外（D1 と R2）に置く

**決めたこと。**
Pi のセッションは DO に残し、長期記憶は D1、消す前の生の記録とスキルのファイルは R2 に置く。

**理由。**

- サーベイは、文脈に作業中の記憶を置き、長期の記録を外の保存先に置く形（Pattern B）から始めて計測することを勧めている（2603.07670）。
  OpenClaw も Hermes も、長期記憶を会話の記録とは別のファイルに持つ。
- 費用で大きいのは書き込みの量と稼働時間であり、保存しているバイト数ではない（下の見積もり）。
  1行あたりや 1 GB あたりでは、DO は D1 より高くない。
  それでも外に置くのは、kodama の事情として次の3つがあるからである。
  - 長期記憶はエージェントの間で共有したい。
  - UI や整理の処理が、エージェントの DO を起こさずに長期記憶を読めるようにしたい。
  - セッション自身の行は、時間とともに消していく。
- D1 は FTS5 と、`batch()` によるトランザクションを持つ。
  R2 は、1 GB あたり D1 の50分の1の値段で大きなものを置ける。

費用の見積もりは次のとおりである。
価格は Cloudflare の料金ページ（Workers Paid、2026年10月時点）から取った。
無料枠はアカウント全体で1か月あたりの量である。

| 項目                        | 価格                                                          | 無料枠     |
| --------------------------- | ------------------------------------------------------------- | ---------- |
| DO の稼働時間               | 100万 GB 秒あたり 12.50 ドル。動いている間、128 MB 分で数える | 40万 GB 秒 |
| DO または D1 の行の書き込み | 100万行あたり 1.00 ドル（削除も数える）                       | 5,000万行  |
| DO または D1 の行の読み取り | 100万行あたり 0.001 ドル                                      | 250億行    |
| DO の SQLite の保存量       | 1 GB 月あたり 0.20 ドル                                       | 5 GB       |
| D1 の保存量                 | 1 GB 月あたり 0.75 ドル                                       | 5 GB       |
| R2 Standard の保存量        | 1 GB 月あたり 0.015 ドル                                      | なし       |
| R2 の書き込みと読み取り     | 100万回あたり 4.50 ドルと 0.36 ドル                           | なし       |

1つのエージェントが1日8時間モデルの出力をストリームし、それを30日続けた場合の、無料枠を超えた分である。

| 費用の出どころ                                                                                                      | 見積もり                   | 減らし方                          |
| ------------------------------------------------------------------------------------------------------------------- | -------------------------- | --------------------------------- |
| ストリーム中の Pi の進捗の書き込み。100 ms（`progress.partialIntervalMs`）ごとに最大1回コミットし、1回で1行以上書く | 860万行以上、8.6 ドル以上  | 間隔を広げる                      |
| モデルの応答を待つあいだの稼働時間                                                                                  | 10万8,000 GB 秒、1.35 ドル | モデルが動く間は避けられない      |
| `subscribe()` のストリームを1日中開けておく（ハイバネーションしない）                                               | 32万4,000 GB 秒、4.05 ドル | 誰も見ていないストリームを閉じる  |
| 会話の記録 1 GB を DO に置いておく                                                                                  | 月 0.20 ドル               | R2 にアーカイブする（0.015 ドル） |

**採らなかった案。**

- **すべてを DO に置く**（エージェントごとと共有の範囲ごとに記憶用の DO を作る）。
  Cloudflare Agent Memory は記憶のプロファイルごとに DO を使っているので、成り立つ形ではある。
  しかし共有の記憶には別の DO が要り、UI や整理の処理が読むたびにその DO を起こすことになる。
- **記憶を R2 の markdown ファイルだけで持つ**（OpenClaw や Hermes がディスクに置くのと同じ形）。
  保存はいちばん安く、人が手で直しやすい。
  しかし検索には別の索引が要り、R2 にはトランザクションが無い。
- **Cloudflare Agent Memory を使う。**
  この設計とよく似ていて、`cf` にはすでに `agentMemory` のバインディングがある。
  ただし非公開ベータなので、記憶の保存先はインタフェースの裏に隠し、あとで差し替えられるようにする。

### 2. compaction は Pi に任せる

**決めたこと。**
Pi の組み込みの compaction を既定のまま使い、フックも置き換えもしない。

**理由。**

- Pi はすでに、切れ目を選び、構造化した形式で要約し、前回の要約を引き継ぎ、失敗したらやり直し、文脈があふれたときにも立て直す。
- 自前の要約が効くという根拠は、別の場面のもの（ACE、2510.04618 が書き直すのは会話ではなく手引き）か、ベンダー自身の測定（Factory の anchored iterative summarization）である。
- 要約を自前で持つと、そのプロンプト、失敗、劣化まで kodama が背負うことになるが、得られるものははっきりしない。
- 要約の弱さ（前提の「要約にすべては残らない」）は、要約を良くするのではなく、事実と生の記録を要約の外に持つことで補う（判断3と判断6）。

**採らなかった案。**

- **`beforeCompact` フックで記憶を抽出し、足し込み式の要約を返す。**
  記憶が Pi の compaction の処理に縛られ、Pi の要約が問題だという根拠も無いまま、要約の質を kodama が背負うことになる。
  評価の確認質問で、記憶と `history_search` では補えない取りこぼしが見えたときのために、選択肢として残す。
- **観測マスク**（古いツール出力を伏せる。2508.21433 では費用を半分にしつつ同等の成績）。
  同じ種類の最適化なので、ツール出力が文脈の大半を占めると測れてから考える。

### 3. 生の記録は R2 に残し、DO からは古い行を消す

**決めたこと。**
compaction で文脈の外に出たエントリを R2 に書き出して確かめ、要約を `archive` の記録として残してから、DO の行を消す。
DO を丸ごと消すことはしない。

**理由。**

- 検索で戻せる圧縮は、要約で上書きするだけの圧縮より強い（2607.08032）。
  OpenClaw も Hermes も Cloudflare Agent Memory も、生の履歴を残している。
  よく使う保存領域から消すのはかまわないが、唯一の写しを消してはいけない。
- OpenClaw は `session.maintenance` で古いセッションを整理し（既定は30日、5,000行）、Hermes は終わったセッションを `prune` で消す。
  消す処理を持つこと自体は既存のシステムでも普通である。
- kodama では compaction は保存領域から何も消さないので、消すのは別の処理にするしかない。
  workerd での実験で、境目より前のエントリと終わったタスクを消しても会話が続き、要約が送られ、`snapshot()` が変わらず、古いリクエスト ID の重複排除も効くことを確かめた。

**採らなかった案。**

- **古い行を消さない。**
  いちばん簡単で、テキストの会話だけなら 10 GB はかなり遠い。
  しかし上限に当たると止まる。
  段階1と2はこの形のままでも動くので、消す処理は計測の結果を見てから入れてもよい。
- **DO を丸ごと消し、引き継ぎメモから始め直す。**
  Pi の公開の API（`reset()` と `deleteAll()`）だけで済み、Hermes が圧縮のたびに続きのセッションを作るのに近い。
  しかし会話の続きが途切れ、マニフェストから戻す処理と世代の番号が要り、購読している人もみな切れる。
  Pi の変更で古い行を消す処理が危うくなったときの、代わりの手段として残す。
- **Pi Durable に公式の削除の API ができるのを待つ。**
  本来はこれがいちばん良い。
  Pi は自分の前提（エントリは不変で ID は使い回さない、fork は親を読む）を知っている。
  上流に提案する価値はあるが、待つほどではないので、消す処理は1つのモジュールにまとめて差し替えられるようにする。

### 4. 記憶を書くのは専用の記憶係だけにする

**決めたこと。**
長期記憶を書くのは記憶係（`MemoryAgent`）だけにする。
仕事をするエージェントが持つのは、検索のツールと `remember` だけである。

**理由。**

- Letta は、記憶の編集を会話するエージェントから外し、sleep-time エージェントに移した。
  記憶の管理と会話を1つのエージェントにまとめると、遅くなり（会話中に記憶の操作を呼ぶ）、信頼性も落ちる（記憶のツールと普通のツールの両方を呼ぶ）からである。
- Cloudflare Agent Memory は、モデルに保存先をそのまま触らせる方式を「本来の作業ではなく、保存と検索の戦略にトークンを使う」と書いている。
- Hermes は、記憶の見直しを主のモデルより安いモデルで走らせられる。
  記憶係のモデルを別に選べるのも同じ考えである。
- 共有ブロックを複数のエージェントが同時に丸ごと書き直すと、更新が失われる（Letta）。
  書き手が1人なら、範囲ごとの書き手が1人に決まり、この問題が起きない。
- sleep-time compute（2504.13171）は、待ち時間に前もって計算しておくと、応答時の計算を減らせることを示している。

**採らなかった案。**

- **仕事をするエージェントが自分で記憶を書く。**
  すべてのリクエストに記憶のツールと指示が載り、仕事用のモデルを記録の管理に使い、1つの範囲に書き手が何人もいることになる。
  Letta がやめた形と同じである。

### 5. 記憶係は `Agent` を継承した内部専用の DO にする

**決めたこと。**
`class MemoryAgent extends Agent` を別のクラスとして公開し、`MEMORY_AGENT` のバインディングでだけ呼ぶ。
`AgentService` からは届かない。

**理由（kodama の事情）。**

- `Agent` と Pi Durable は、永続的な受け付け、リクエスト ID による重複の排除、順に処理する受付の列、復旧をすでに持っている。
  記憶係の仕事はこれらをそのまま使える。
- 継承したクラスに別のバインディングを持たせると、公開の RPC から届かないことと、ツールが別の登録表にあることが、どちらも構造で保証される。

**採らなかった案。**

- **記憶係を Cloudflare Workflow にする。**
  Workflows はモデルを待つあいだ課金されないが、`Agent` がすでに持つものを、別の実行の仕組み、別のツール、別のテストで作り直すことになる。
  節約できる稼働時間も小さい（判断1の見積もりで、待ち時間の稼働は月 1.35 ドル）。
- **公開の名前空間にある、予約した ID の `Agent` にする。**
  公開の RPC のすべてのメソッドでその ID を弾く必要があり、ツールの制限も設定の検査に頼ることになる。

### 6. 書き込みは、その場の `remember`、アイドル時の抽出、毎日の統合の3つ

**決めたこと。**

- ユーザーが頼んだときと、エージェントが残すべきと判断したときは、そのターンの中で `remember` を呼び、記憶係がすぐ書く。
- エージェントがしばらくアイドルになったときと古い行を消す前に、会話の記録から抽出する。
- 1日1回、統合する。

**理由。**

- 既存のシステムは、どれもこの3種類のどれかを持っている。

  | きっかけ         | 既存のシステム                                                                                                                          |
  | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
  | その場で明示的に | Cloudflare Agent Memory の `remember`、Hermes と OpenClaw の memory ツール                                                              |
  | 裏で会話から     | Grok Build（ターンが終わるたび）、Hermes（ターン後の見直し）、Cloudflare Agent Memory（compaction の時点）、OpenClaw（compaction の前） |
  | 定期的にまとめて | OpenClaw の dreaming、Grok Build の `/dream`、Devin の dreaming（1日1回ほど）                                                           |

- 抽出は compaction からではなく、会話の記録から行う。
  OpenClaw が compaction の直前に記憶を書き出すのは、文脈がエージェントの見る唯一の場所だからである。
  kodama では compaction は保存領域から何も消さないので、エントリは消すまで `scanEntries` で読める。
- 記憶システムの誤りは、抽出と更新の段階で生まれて溜まる（HaluMem、2511.03506）。
  過去の誤りが次の誤りを呼ぶ（2505.16067 の error propagation）。
  そのため抽出した候補は、根拠のエントリと突き合わせて裏付けのないものを捨て、出どころを付けて保存する。
- エージェントの判断による保存は、頼まれた保存より弱く扱う（重要度を低めにし、重複や価値の低いものは断り、使われなければアーカイブする）。
  Hermes も、頼まれずに会話の中で出ただけの事実は記憶しない。
  ふつうの利用者でも記憶に細工できる（MINJA、2503.03704）ので、頼まれていない保存を無条件に受け入れない。

### 7. 記憶は4つの種類に分け、事実は置き換え、出来事は薄れさせる

**決めたこと。**
`fact`、`instruction`、`event`、`task` に分ける。
`fact` と `instruction` は話題キーを持ち、同じキーの新しい記録が古い記録を置き換える。
`event` は新しさで順位を下げる。

**理由。**

- 4つの種類と、話題キーによる置き換え（消さずに `superseded` にする）は、Cloudflare Agent Memory と同じである。
- Mem0（2504.19413）は、新しい候補ごとに ADD、UPDATE、DELETE、NOOP を選ぶ。
  抽出の手順4（追加、置き換え、無効化、何もしない）はこれに当たる。
- 事実に時間の減衰をかけるのは種類の取り違えである（2604.11364）。
  Zep（2501.13956）は、古くなった事実を辺の無効化で扱う。
  出来事には新しさの減衰が効く（Generative Agents、2304.03442 の減衰係数 0.995）。
- モデルは古くなった事実をそのまま受け入れがちである（STALE、2605.06527 で正答率 55.2%）。
  置き換えは明示的に記録する。

**採らなかった案。**

- **人ごとの範囲を持つ**（Hermes の Honcho は相手ごとに別の peer プロファイルを持つ）。
  kodama の事情として、相手の記憶は要らないと決めた。

### 8. 常に読み込む記憶は小さく固定し、区切りでだけ変える

**決めたこと。**
常に読み込む記憶は、エージェント分 2,200 文字、共有分 1,000 文字に収める。
DO に写しを置き、起動時とアイドル中の通知でだけ更新する。

**理由。**

- Hermes の `MEMORY.md` は 2,200 字で、セッション開始時に固定する。
  固定するのは、プロンプトのキャッシュを効かせるためである。
- Pi は、セクションが変わるとそれを新しいシステムエントリとして送り直す。
  ターンの途中で変えると、そのたびに書き込みとキャッシュの取り直しが起きる。
- 予算の使用量を表示する形（`[67% — 1,474/2,200 chars]`）は Hermes と同じである。

### 9. 検索は D1 の FTS5 と Intl.Segmenter で始める

**決めたこと。**
`Intl.Segmenter` で語に分けた文字列を FTS5（`unicode61 remove_diacritics 2`）で索引にし、BM25 で並べてから新しさと重要度で並べ直す。
ベクトル検索は最初の版には入れない。

**理由。**

- Hermes の `session_search` は SQLite FTS5 である。
  OpenClaw の組み込みの検索も SQLite の BM25 から始まり、ベクトルは埋め込みの提供元を設定したときだけ足される。
- サーベイは、単純な形から始めて計測することを勧めている（2603.07670）。
- D1 で FTS5 と `Intl.Segmenter` を組み合わせて日本語の全文検索を作った例がある（zenn、coji）。
- `Intl.Segmenter` が workerd でも Node と同じ結果になることを確かめた。
  「使う」「リポジトリ」「リポ」「デプ」「マネージャー」「レビュー」「サーバレス」と「サーバーレス」「ベストプラクティス」「ＰＮＰＭ 使う」は当たった。

**採らなかった案。**

- **FTS5 の trigram のトークナイザを使う。**
  trigram は3文字以上の問い合わせが要るので、「使う」や「リポ」のような2文字の語が引けない。
  索引も文字の位置ごとに作るので大きくなる。
  `unicode61` だけでは、空白の無い日本語の文が丸ごと1語になる。
- **最初からベクトルと RRF を入れる**（Cloudflare Agent Memory、OpenClaw のハイブリッド検索）。
  まず全文検索で始め、取りこぼしを計測してから、ベクトルを足すかを決める。

### 10. 手順はスキルにし、Pi の標準の読み方で読ませる

**決めたこと。**
スキルは Agent Skills の形式で R2 に置く。
一覧は `skills` セクションに名前、説明、パスで出し、本体はモデルが Pi の `read` ツールで読む。
`read` が読む先は、R2 に対応させた読み取り専用の `ExecutionEnv`（`SkillsEnv`）である。

**理由。**

- どの既存のシステムも、手順は事実と分けてスキルとして持ち、名前と説明だけを先に見せる（Anthropic の progressive disclosure）。
- Claude Code は「複数の手順からなる内容は、スキルに移す」と書いている。
- Pi のスキルも、名前と説明を一覧に出し、本体はモデルが `read` で読む。
  同じ読み方にしておけば、付属のファイルを相対パスで指すスキルがそのまま動く。

**採らなかった案。**

- **スキル専用のツールを作る**（`skill_load` と `skill_search`）。
  Pi の `read` ツールと役割が重なり、付属のファイルを相対パスで指すスキルが動かなくなる。

### 11. スキルは検証できた経験からだけ作り、少なく保つ

**決めたこと。**
少なくとも2回成功した手順からだけ作り、チェックを通ったら有効にする。
一覧は最大50件にし、使われないスキルは stale にしてからアーカイブする。

**理由。**

- 成功して検証できた軌跡から作ったスキルは効いた。
  AWM（2409.07429）で相対 24.6% と 51.1%、ASI（2504.06821）で 23.5%（検証の仕組みが効いたと書いている）。
  ReasoningBank（2509.25140）は、成功だけでなく失敗からも教訓を取り出す。
- 作業の前にエージェント自身が書いたスキルは、スキル無しより 8.1〜11.5 ポイント悪かった（SkillsBench、2602.12670）。
  同じ論文で、3つ以下の部品に絞ったスキルは大きな束より良かった。
- 更新を重ねると、その回だけの事情が混ざって散らかる（SkillEvolBench、2605.24117）。
- 一覧から選ぶ精度は、16〜32個で 96〜98%、64個で 92%、128個で 78% と落ちる（2607.10113）。
  50件の上限はこの数字から取った。
- Hermes の curator は、14日使われなければ stale、30日でアーカイブし、自動では消さず、固定したものは対象外にする。
  統合でまとめたスキルには `absorbed_into` を付ける。
  エージェントのスキルの数字と `absorbed_into` はこれに合わせた。

### 12. スキルはエージェント固有と共有の2つの範囲に分ける

**決めたこと。**

- スキルの範囲は `agent:<agentId>` と `shared:<space>` の2つにし、エージェントが読む共有の範囲は `sharedSpaces` で決める。
- 同じ名前なら、エージェントのスキルが共有のスキルを隠す。
- スキルはまずエージェントのスキルとして生まれ、2つ以上のエージェントが同じ手順を持ったときに、レビューを通して共有に上げる。
- 共有のスキルは、受け入れられた提案を通してしか変わらない。
- スキルの更新はその場で上書きし、変更前のファイルを変更記録から戻せるようにする。
- 共有のスキルの片付けは、どのエージェントも使わなくなってからにし、期間も長くする。

**理由。**

- 範囲の重ね方と隠し方は、既存のシステムと同じである。
  Hermes は、プロジェクト、ローカル、外部のディレクトリの順に優先し、同じ名前は優先度の高い方が隠して、隠した方を記録に残す。
  プロジェクトのスキルが同じ名前のスキルに勝つのは「その場所では持ち込んだスキルが勝つ」ためだと書いている。
  Pi も、同じ名前は先に見つけた方を使い、警告を出す。
  一覧に同じ名前が1回しか出ないのはこれに合わせた。
- 共有のスキルを書き手から守るのは、構造で行う。
  Hermes では、エージェントが作ったスキルはローカルに書かれるが、既存のスキルは見つかった場所で直接書き換えられる。
  ドキュメントも「外部のディレクトリは書き込みの防壁ではない」と書き、守りたければファイルの権限で分けるよう勧めている。
  kodama では、記憶係の `skill_write` がエージェントの範囲しか受け付けず、共有のスキルは `apply_proposal` でしか書かれない。
- 共有に上げるときにレビューを挟むのは、共有の記憶と同じ理由である（判断13）。
  悪意ある「成功体験」を植え付けると長く残る（MemoryGraft、2512.16962）ので、共有のスキルはとくに危ない。
  Collaborative Memory（2505.18279）も、書き込みの方針で個別と共有のどちらに置くかを選び、出どころを変えられない属性として付ける。
- 2つ以上のエージェントで同じ手順が成功したことは、1つのエージェントの事情ではない根拠になる。
  これは判断11の「検証できた経験から作る」を、エージェントをまたいで当てはめたものである（kodama の事情）。
- 上書きと変更記録は Hermes と同じ形である。
  Hermes はスキルを見つかった場所でそのまま書き換え、版を並べて持たない。
  そのかわり、スキルへの変更をすべて追記だけの記録に残し、ファイルごとの変更前と変更後の SHA-256 を付け、中身はハッシュをキーにして重複なく保存する。
  1件の変更だけを巻き戻すことも、消したスキルを戻すこともできる。
  上書きなら、今の版を指す番号を D1 と R2 で揃え続ける必要がなく、変わったファイルだけが blob として増える。
- 共有のスキルを長めに残すのは、レビューを通っていて、使うエージェントが複数いるからである。
  Hermes の curator は、既定ではエージェントが作ったスキルしか片付けない。
  同梱のスキルが黙って消えると、壊れたように見えるからだと書いている。
  kodama は共有のスキルも片付けるが、期間を2倍にし、アーカイブしたものは戻せるようにする（kodama の事情）。
- エージェントごとの上書きは、Hermes のプロジェクトのスキルと同じく、その場所でだけ勝つ形である。
  上書きが何件も同じ方向に揃ったら、共有のスキルを直す根拠として提案に回す（kodama の事情）。

**採らなかった案。**

- **版ごとに R2 のディレクトリを分ける**（`skills/<scope>/<name>/v<version>/`）。
  読んでいる途中のファイルが入れ替わらない利点はあるが、変わらないファイルまで版ごとに写すことになり、今の版の番号を D1 と R2 で揃え続ける必要がある。
  既存のシステムにこの形の例は無い。
- **共有のスキルだけにする**（全エージェントで1つの一覧を持つ）。
  1つのエージェントでしか成功していない手順が全員に配られ、判断11の根拠と合わない。
  一覧も全員分の数に膨らむ。
- **エージェントのスキルだけにする。**
  同じ手順を各エージェントがそれぞれ覚え直すことになり、改善も共有されない。

### 13. 共有の記憶はレビューを通して書き、出どころを残す

**決めたこと。**
共有の範囲には、記憶係が作った提案がレビューで受け入れられたときだけ書く。
受け入れた提案は新しい版の記録になり、その場で書き換えない。
信頼できない出どころの内容は出どころ付きの `event` として残し、レビューなしで固定しない。
秘密情報は書く前に伏せる。

**理由。**

- ふつうの利用者でもエージェントの記憶に細工できる（MINJA、2503.03704）。
- 既存のプロンプトインジェクション対策では、記憶の汚染を防げない（MPBench、2606.04329）。
- マルチエージェントの記憶でいちばん大きな課題は整合性であり、記憶への出入りを細かく制御する必要がある（2603.10062）。
- Collaborative Memory（2505.18279）は、個別と共有の2層に分け、読み書きの方針で見える範囲を決め、出どころを変えられない属性として残す。
- OpenClaw は、信頼できない出どころの報告は、信頼できるレビュー役が確かめるまで記憶にしないと書いている。
- Hermes は、記憶の書き込みをインジェクションと持ち出しの型で検査してから受け入れる。
- Cloudflare Agent Memory も、記憶のプロファイルを複数のエージェントと人で共有する形を示している。
  共有すること自体は普通の形である。

## 根拠が弱いところ

確定させる前に見ておくべき点である。

- **本番の `databaseSize` が古い行を消したあとに減るか**は確かめていない。
  ローカルでは 20.5 MB から 5.1 MB に減った。
- **古い `submissions` を消しても安全か**は確かめていない。
- **進捗のコミット1回で何行書くか**は測っていない（段階1で測る）。
  判断1の費用の見積もりは、ここが1行だとした下限である。
- **日本語の検索の取りこぼし**として、「プラクティス」だけでは「ベストプラクティス」に当たらない。
- **スキルの更新の途中に読むと、新旧のファイルが混ざりうる。**
  付属のファイルを先に、`SKILL.md` を最後に書き、更新は統合の中でしか行わないので、受け入れる（Hermes も同じ）。
- **共有のスキルの片付けの期間（30日と60日）、共有に上げるのに要るエージェントの数（2）、一覧の上限（50）**は、外の根拠をそのまま使ったものではない。
  50は 2607.10113 の数字から余裕を取ったもので、残りは kodama の事情で決めた。
- **調べたが原文に届かなかったもの。**
  X の @grok の記憶の仕組みは公式の資料が見つからなかった。
  Hermes の Issue #22620（スキル一覧が膨らんで文脈が増える）と OpenClaw の Issue #45608 は、GitHub が 403 を返して読めなかった。
  同じセッションで何十回も圧縮を回し、要約の作り直しと足し込みを比べた独立の測定も見つからなかった。
- **資料どうしで食い違ったもの。**
  OpenClaw のセッションが毎日自動で捨てられるかは、zenn の記事（毎日午前4時に破棄）と公式のドキュメント（既定は自動リセットなし）で食い違う。
  公式のドキュメントを採った。
