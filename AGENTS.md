# Repository Guidelines

## Project Structure & Module Organization

Kodama runs Pi Durable agents on Cloudflare Durable Objects, with one SQLite-backed object per agent ID. The pnpm workspace contains `packages/agents` and `packages/ui`. `packages/ui` is the SvelteKit web UI, which for now exists only as Storybook mockups with mock data and no network requests (`packages/ui/README.md` lists its stages). Its design system lives in `design/` (not a workspace package).

- `packages/agents/src/index.ts`: the single default service-binding RPC entrypoint (`AgentService`) for conversations, registry and configuration management, and cron. Conversation methods admit only registered working agents by UUID.
- `packages/agents/drizzle/`: every Drizzle schema, next to the migrations drizzle-kit generates from it, one folder per database. There are two D1 databases. `memory/` is long-term memory (`kodama-memory`, bound as `MEMORY_DB`): `memory/schema.ts` is its schema and `memory/migrations/` its migrations (apply them with `cf d1 migrations apply <memory-database-id> --dir drizzle/memory/migrations`). `management/` is the management database (`kodama-management`, bound as `MANAGEMENT_DB`): the agent registry, configuration versions, principals, members, settings, and audit, with `management/schema.ts` and `management/migrations/` (apply them with `cf d1 migrations apply <management-database-id> --dir drizzle/management/migrations`). `durable-object/schema.ts` is kodama's tables in each Durable Object's own SQLite, and `durable-object/migrations/` their migrations, which `src/agent/local-db/local.ts` applies. Keep one schema file per SQLite database. Edit the schemas by hand; never edit the `migrations/` folders.
- `src/lib/`: generic helpers that import nothing else from `src/` (`hash.ts`, `search-text.ts`, `uuid.ts`, `errors.ts`, `sql.ts`, `deadline.ts`, and `serial.ts`, the ordering helpers the `Agent` class uses).
- `src/credentials/`: encrypted vault, management flows, agent-local resolution, and local bootstrap. Keep all credential code here. Credentials are supplied only for provider authentication; do not add output redaction or a redaction knowledge cache. Management/assignment/invalidation/bootstrap flows belong to the top service layer; the rest follows the credential-storage dependencies in `docs/agents.md`.
- `src/control-plane/`: the management database through Drizzle, configuration versions, and models: `db.ts` the handle, `installation.ts` the lazily initialized stable installation identity, `registry.ts` registry rows, admission, and resolving references, `versions.ts` configuration versions, `lifecycle.ts` lifecycle states and their moves, `principals.ts` the caller as a principal, `audit.ts` the audit row, `config.ts` configuration settings, `models.ts` provider catalogs, and `usage.ts` accounting queries. It knows nothing of objects.
  - `workflows/`: management flows called by `AgentService` (`agents.ts`: create, list, rename, versions, pushing to objects), the seed (`seed.ts`: the memory agent's registry row and the first agent, a general-purpose assistant), daily reconciliation (`reconcile.ts`), and usage reporting (`usage.ts`). It sits at the top with the entrypoint; the rest of `src/control-plane/` does not import it.
- `src/agent/`: the `Agent` Durable Object, a working agent and the base of `MemoryAgent`; do not introduce a separate `WorkingAgent` class. `agent.ts` wires the parts and serves RPC. `config.ts` registers working-agent models and tools; `memory.ts` refreshes memory and queues extraction; `memory-extension.ts` wires memory tools and prompt hooks into Pi.
  - `runtime/`: shared execution functions only: `harness.ts` opens Pi and provides common settings and its exclusive section; `alarms.ts` handles shared alarms and recovery; `events.ts` streams SSE; `pruning.ts` schedules pruning and enforces storage limits; `views.ts` maps Pi state to RPC reads; `config-apply.ts` applies or holds versions; `restrictions.ts` checks external calls. No agent classes, tool registration, or working-agent memory policy belongs here.
  - `local-db/`: opening kodama's tables in each Durable Object's own SQLite (`local.ts`; the schema is `drizzle/durable-object/schema.ts`), `memory.ts` the local memory cache, remember quota, and extraction progress; `memory-jobs.ts` the memory agent's job queue; `external-data.ts` legacy contact metadata and the known URLs fetch may reach on every call; `contacts.ts` the tracked peer outbox, receiver receipts, retention, and atomic completion notifications; `usage.ts` model invocation usage; `pruning.ts` pruning runs and Pi-row queries; and `pi-tables.ts`, Pi Durable's tables as pruning reads them; re-run `src/memory/prune/prune.test.ts` and `src/agent/runtime/harness.test.ts` on every Pi upgrade.
  - `dedicated/`: internal agents that support Kodama, implemented as `Agent` subclasses in the same `AGENTS` namespace under reserved names. They retain `kind = 'dedicated'` in the registry and are unreachable through the working-agent RPC. Never add a Durable Object class or binding for a dedicated agent; add a folder under `dedicated/`, a reserved name with `:`, and a `DEDICATED_AGENTS` entry in `src/agent-object.ts`.
    - `memory/`: the memory agent, and only what it adds to an agent: `agent.ts` the `MemoryAgent` class, which extends `Agent`, overrides its protected hooks, and adds the job methods; `config.ts` its model, configuration, harness options, tool set, and prompts; `runner.ts` enqueueing, the drain, retries, and consolidate. Queue persistence lives in `src/agent/local-db/memory-jobs.ts`, its dedicated tool adapters in `src/tools/memory/curator/`, and memory workflows in `src/memory/`.
- `src/agent-object.ts`: exports `AgentObject`, the one Durable Object class (exported as `Agent`), whose constructor selects a working agent or the system agent registered for the object's name in `DEDICATED_AGENTS`.
- `src/validation.ts`: valibot schemas for untrusted RPC input; failures throw `TypeError`.
- `src/tools/`: model-facing tool definitions, argument schemas, tool-specific execution workflows, and result formatting. `web/` keeps web definitions, admission/rate-limit orchestration, transports, parsers, and their tests together; `web/providers/` houses external provider implementations; `contact.ts` defines tracked peer delivery and result-read tools through the supplied agent operation; `src/agent/contact.ts` owns durable provenance, delivery, and receipt collection. Tools receive shared state and operations rather than importing agent classes. Keep agent lifecycle hooks, peer delivery, memory workflows, and persistence in their existing layers. `index.ts` registers optional general tools; `memory/working.ts` defines working-agent memory tools; `memory/curator/` contains only the memory agent's dedicated tools and their helpers. Keep these tool sets separate; neither imports the other's adapters. Call workflows or store functions; never construct database queries here. `src/agent/memory-extension.ts` wires working-agent tools and hooks into Pi.
- `src/memory/`: long-term memory, one folder or file per part. Keep each file to one concern; split a file before it grows past a few hundred lines, but do not split one that small.
  - `store/`: D1 through Drizzle, with the schema in `drizzle/memory/schema.ts`. `records.ts` applies write operations, `record-plans.ts` and `progress-plans.ts` plan them, `statements.ts` holds the statements they share, `search.ts` searches records; `queries.ts` reads records and prompt revisions; `archive.ts` reads and writes the archive catalog; `skills.ts` persists skills; `maintenance.ts` performs retention and consolidation queries; `job-results.ts` reads operation results and records terminal job failures. Write queries with Drizzle's query builder and migrations only with drizzle-kit; do not write SQL by hand.
  - `extraction/`: context (`context.ts`), entry reads (`entries.ts`), record evidence (`records.ts`), and permission-checked writes (`operations.ts`), independent of the model-facing tool API.
  - `consolidation.ts`: daily consolidation: retention, skill curation, and the consolidate jobs it queues.
  - `working/`: prompt assembly and refresh (`always-loaded.ts`), remember-request workflow (`remember.ts`), and their dependencies. Tool definitions and Pi extension wiring live above this layer.
  - `archive/`: archived segments in R2 (`segment.ts` writes, `reader.ts` reads) and `history_search`.
  - `prune/`: pruning of old Pi entries: limits, runs, the steps before the delete, and the delete.
  - `skills.ts`: pure skill types, naming rules, size limits, and write validation; no persistence.
  - `shared.ts`: checked writes to shared spaces (two agents' records, or the space's own).
  - `jobs.ts`: the memory agent's input contract; `transcript.ts`: the text of Pi entries and paged entry reads.
- `src/protocol.ts`: transport types; consumers should use type-only imports.
- Tests sit next to the code they test, as `<module>.test.ts` in the same folder (for example `src/agent/agent.test.ts` for the Agent RPC and `src/memory/prune/prune.test.ts` for pruning); each `drizzle/<database>/schema.test.ts` checks its schema against its migrations. Name every test file after its module; a test with no module of its own belongs in the test of the module it exercises. Shared test helpers are in `src/testing/` and the Vitest setup is `vitest.setup.ts`; production code never imports either.
- `design/`: the UI design system, exported from the Kodama Design System artifact: `README.md` the brand book, `sveltekit.md` the implementation guide, `tokens.json` the tokens (`tokens.css` is generated from it), `components/<Name>/` a guide (`README.md`) and a live preview (`preview.html`) per component, `components/bundle.js`, `bundle.css` and `index.d.ts` the shared preview code, styles and prop types, and `images/` rendered screens. Fonts are not stored: `tokens.css` imports Gen Interface JP from the `gen-interface-jp` npm package through jsDelivr. Change the design in the artifact first, then export it here.
- `packages/ui/`: SvelteKit 3, Tailwind CSS v4, and shadcn-svelte, built from `design/`. Its source follows Feature-Sliced Design: layers `app`, `pages`, `widgets`, `features`, `entities`, and `shared`, each importing only the layers below it, through the `#app/*` and `#shared/*` aliases; SvelteKit's `src/routes/`, `src/app.html`, and `src/app.d.ts` stay where SvelteKit expects them, and Kodama's own components go into the layers above `shared` as they are built. `src/app/styles/index.css` maps the tokens to utilities with kiso.css as the reset, `src/shared/styles/tokens.css` is a copy of `design/tokens.css` without its CDN font imports (its test fails when they differ), `src/shared/ui/` holds the general-purpose UI kit in the shape of shadcn-svelte's, built on native elements where the platform has them (`<dialog>`, the Popover API, invoker commands, focusgroup, interest invokers, the customizable `<select>`, a `switch` checkbox), with a polyfill only for features short of Baseline (`interestfor`, loaded on demand from `src/shared/lib/polyfills.ts`), and on bits-ui otherwise (variant tables in `variants.ts`, which type-aware Oxlint can read; native element styles in `src/shared/styles/native.css`), `src/shared/lib/` the helpers they share, and stories sit in the folder of what they show as `<Name>.stories.svelte` (the token stories next to `src/shared/styles/tokens.css`, compositions in the folder of the component they build on, and the introduction page in `src/app/`). Storybook lists the parts fit for any use under Primitives and those made for one use under Patterns. Its Svelte tooling is [rsvelte](https://github.com/baseballyama/rsvelte), the Rust port of the Svelte compiler: the `pnpm-workspace.yaml` override points `@sveltejs/vite-plugin-svelte` at `@rsvelte/vite-plugin-svelte`, `rsvelte-check --tsgo` type-checks it with TypeScript 7 (`@typescript/native`, an alias of `typescript@7`), and `typescript` 6 stays installed only for the JS API that `svelte-kit sync` calls.
- `packages/agents/cloudflare.config.ts`: Worker bindings (`AGENTS`, `MANAGEMENT_DB`, `MEMORY_DB`, `ARCHIVE`), the default entrypoint `AgentService`, secrets, and SQLite configuration.

The abbreviated `src/` paths above are relative to `packages/agents/`.

Keep the code functional and simple. Classes exist only because a Durable Object or a Worker entrypoint (`AgentService`) must be one: `Agent`, its dedicated subclasses such as `MemoryAgent`, and `AgentObject`, which picks between them. They hold the object's in-memory state in private fields; a subclass changes behavior only through `Agent`'s protected hooks, and a method only it serves is declared on `Agent`, which rejects it. Write everything else as plain functions that take what they need (`db`, `local`, `harness`, `env`) and return a result; do not add classes, or objects that only carry dependencies, to organize code. Prefer fewer, cohesive files over many small ones, and the simplest storage that stays correct after a stop (for example one D1 batch rather than a journal over R2). Add a mechanism only when the feature needs it now.

Imports follow the layers in `docs/agents.md` (Dependencies): `lib` imports nothing else from `src/`, the memory parts never import `src/agent/runtime/`, `src/agent/agent.ts`, or `src/agent/dedicated/` (they use `src/memory/jobs.ts`). `src/agent/` sits above `src/agent/runtime/`, and `src/agent/dedicated/` above both; the runtime never imports either agent layer. `src/agent-object.ts` selects between them at the composition boundary. `src/control-plane/` outside `workflows/` imports no agent code, and `src/control-plane/workflows/` sits at the top with the entrypoint. The memory agent is a `MemoryAgent` object in the `AGENTS` namespace, not its own Durable Object class or binding. All tool definitions and tool-specific execution live in `src/tools/`; memory workflows never import them. Tools may use shared runtime helpers but never import agent classes. RPC validation may reuse pure web argument normalization. D1 queries live in `src/memory/store/`, object SQLite queries in `src/agent/local-db/`, and R2 encoding/IO in `src/memory/archive/`. Pure memory contracts (`jobs.ts`, `skills.ts`, and the `RunningJob` type) may be used by persistence. Put new code in the lowest layer it fits.

`docs/agents.md` explains the runtime, `docs/memory.md` long-term memory, `docs/testing.md` how the tests run (the shared workerd runtime and CI sharding), `docs/mcp.md` the MCP client, and `docs/single-operator.md` the single-operator trust boundary. Keep documentation in `docs/`, not in packages. File comments cite
their sections by name, so keep the headings and the code in step when either changes.

## Build, Test, and Development Commands

mise installs the toolchain pinned in `mise.toml`: Node.js, pnpm 12.14.0, and the Vite+ CLI `vp`. Run `mise install` once, then use `vp`: `vp install` for dependencies and `vp run <script>` for `package.json` scripts. `vp build` and `vp test` are Vite+ built-ins, not the scripts of those names.

- `vp install`: install workspace dependencies.
- Copy `packages/agents/.dev.vars.example` to `packages/agents/.dev.vars` and set a development `CREDENTIAL_KEK_V1` (base64 of 32 random bytes).
- `vp run dev:agents`: start the local Worker; it exposes RPC, not a browser page.
- `vp run agent dev seed-credentials < /secure/path/provider-keys.json` registers provider keys into local D1 and assigns both agent kinds; then `vp run agent seed` and `vp run agent send assistant "Hello"`: create the starting rows, then send to the first agent by its slug through the development adapter to Durable Object RPC; see `vp run agent --help` for history and cancellation.
- `vp run check`: run the type checks (`tsrs` for agents and `rsvelte-check --tsgo` for UI), type-aware Oxlint with rsvelte's Svelte rules, Oxfmt and Svelte formatting checks, and tests. If `tsrs` fails, try `vp run typecheck:compat` to check agents with TypeScript's own `tsc` (which CI runs); the UI uses `rsvelte-check --tsgo` in both commands.
- From `packages/ui`, `vp run storybook` starts the Storybook mockups and `vp run build-storybook` builds them.
- `vp run test`: run workspace tests.
- From `packages/agents`, `vp run test:coverage` runs the tests with Istanbul coverage (text summary and `coverage/` HTML report).
- `vp run format`: format the repository through Vite+ and `.svelte` files through `rsvelte-fmt`, sharing the root `vite.config.ts` settings via `scripts/format-svelte.ts`; review resulting changes.
- From `packages/agents`, `vp run build` builds without deploying, and `vp run cf:types` regenerates runtime types.
- From `packages/agents`, `vp run db:generate:memory` writes a D1 migration after `drizzle/memory/schema.ts` changes, `vp run db:generate:management` one after `drizzle/management/schema.ts` changes, and `vp run db:generate:durable-object` a local migration after `drizzle/durable-object/schema.ts` changes (add it to `src/agent/local-db/local.ts`); tests fail when they differ.

## Coding Style & Naming Conventions

Use strict TypeScript with two-space indentation, single quotes, no semicolons, trailing commas, and a 100-column formatting width. Vite+ runs Oxfmt (`vp fmt`) for formatting and type-aware Oxlint (`vp lint`) for type safety, both configured in the root `vite.config.ts`; `rsvelte-fmt` adds `.svelte` formatting with the same settings, and `@rsvelte/oxlint-plugin` adds Svelte lint rules. Use type-only imports and handle promises explicitly. Never use `any`, type assertions (`as Type` or `<Type>`), non-null assertions, or TypeScript suppression comments (`@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`). Const assertions (`as const`) are allowed. Fix the types and implementation instead of disabling lint rules, weakening checks, or using an equivalent workaround.

Document with TSDoc: every file opens with a module comment ending in `@module`, and every export has a `/** */` comment that states intent and non-obvious constraints without restating the types. Cite the docs with `@see docs/memory.md — Section`, and use `@param name - text`, `@returns`, `@throws {@link TypeError} When …`, and `@remarks` only where they add something.

Follow existing camelCase functions, PascalCase types/classes, and lowercase hyphenated filenames such as `current-time.ts`. Write comments and repository documentation in English.

## Testing Guidelines

Use Vitest through Vite+ (import test APIs from `vite-plus/test`) with the Cloudflare plugin in workerd. Put each test next to the module it tests as `<module>.test.ts` (not in a separate `test/` folder) and describe observable behavior. Put shared mocks and helpers in `src/helper/` instead of copying them; do not add other test-only folders or files that are not `*.test.ts`, and split a test file by `describe` before it grows past a few hundred lines. Mock external model requests while exercising real RPC, SQLite persistence, eviction, and alarms. Tests require no real API keys. No numerical coverage threshold is configured; add regression tests for changed behavior and run `vp run check` before submitting.

## Commit & Pull Request Guidelines

There is no commit history yet. Use Conventional Commits, for example `feat(agents): add tool registration`. Keep changes focused. PR descriptions should explain behavior changes, link relevant issues, and report checks performed and any limitations.

## Security & Configuration

Never commit `.dev.vars`, provider credentials, or generated `.cloudflare/` state. Keep provider credentials in the encrypted management D1 vault; only the single `CREDENTIAL_KEK_V1` belongs in Worker secrets. Never add an environment or file credential fallback. Keep plaintext and ciphertext out of settings, RPC results, logs and memory; see `docs/credentials.md` for cache bounds and the read-only Worker Secret boundary. Preserve the private RPC boundary; future UI Workers must authenticate users and authorize access to agent IDs. Only the agents Worker binds D1: the UI Worker never binds a D1 database and reaches the registry and configuration only through the default `AgentService`.
